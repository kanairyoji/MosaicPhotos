## 2. 指標の既知の穴

1. **負担が外部化される部品を、ファイル単位の churn は取りこぼす。** 実例: 背景ゲート網は
   自分のファイルが 551 行・fix 6 件しかないのに、**述語の使い方を直した fix が 19 件**あった
   （うち 10 件が「解析が進まない」系）。素点では最下位だった。→ `外部fix` を足して補正。
   共有される判定（ゲート・ID 採番・キャッシュ鍵）は**使う側が壊れる**ので、この列を必ず見る。
2. **（2026-09-21 に修正）「可変状態」が 3 つの別物を数えていた。** 行頭の `var` を
   無差別に数えていたので、**関数内のローカル変数**と**計算プロパティ**と
   格納プロパティが同じ列に入っていた。重み 13（構造系で最大）なので、**順位そのものが
   歪んでいた**。実測の内訳:

   | 領域 | 旧「状態」 | 実際の格納プロパティ | ローカル変数 | 計算プロパティ |
   |---|---:|---:|---:|---:|
   | 顔クラスタ後処理 | 166 | **64** | 95（57%） | 7 |
   | 家族共有 | 180 | **109** | 53 | 18 |
   | 解析状況/ブースト | 43 | **20** | 3 | 20（47%） |
   | 解析トリクル起動 | 2 | **0** | 2 | 0 |

   計算プロパティは**状態を減らす書き方**なので、加点すると逆向きの誘導になる。
   ローカル変数は手続きの長さの代理指標だが、それは `maxBranches` が見ている。
   ⚠️ Codable の DTO フィールド（`ShareAnalysisData` の `x` `y` `w` `h` …）は
   **数えたまま**にした——型が持ち越す値ではある。家族共有の 109 はこれを含む。
3. **「対策の効き」は測れない。** 下の表の効き・確度・難度は判断で、根拠は本文に書く。
4. **大きい＝複雑とは限らない。** `JapaneseVisualLexicon`（454 行）はデータ表、
   `FaceClustering`（606 行）は純ロジックでテスト済み・fix 履歴も少ないので領域に入れていない。
5. **リファクタのコミットも `fix(` なら fix に数える。** ADR-197 のような「自分の判断の撤回」は
   潜在欠陥ではないが履歴を押し上げる。★ の領域はこの影響を受けている。

### 効きの見積もりを更新した理由（第 1 回 → 第 2 回）

実際に 3 領域をやってみて分かったこと:

- **「判断を純ロジックの表・手順に出す」は想定より効いた。** 夜間窓のテストが 0 → 49 本、
  ゲート網が 33 → 120 本。テストが書けなかった場所に守りができる効果を、前回は過小評価していた。
  → 同じ型が効く #6 の確度を 0.75 → **0.82**、#1 を 0.75 → **0.78** に上げた。
- **行数は減らない。** ADR-196 の実測は **+266 行**（コメント除く）。消えたのは*概念*
  （述語 11→1・状態 4→2・コピー 3→1）で、増えたのは表の明示とテスト可能な純ロジック。
  **「効き」は行数ではなく欠陥率の話**だと読み替える必要がある。
- **良い構造は選択肢を安くする。** ADR-197 で設定を 2 つ戻すコストが「表の行 1 つ＋トグル 1 つ」
  で済んだ。**「構造を単純にするために設定を減らす」は成立しない**（ADR-197 の教訓）。
- **条件を 1 つにまとめると、テストが環境依存になる。** 述語の入力が狭いうちは表面化しないが、
  まとめた途端に「低電力モードの Mac だと落ちる」テストになった。DI の seam を同時に用意する。

## 6. 次の候補

**第 3 回時点で、上位 3 つ（#6 / #2 / #1）は ADR-198 で着手済み**。残るのは以下。

1. **#7 AI増分再評価**（構造 15・結合 5 ＝作業が安全）— `refreshIncremental` 131 行・分岐 36 で、
   評価済み件数・待機列・埋め込み総数の頭打ちという**帳簿 3 つを手で整合**させている。
   結合が 5 しかないので、壊しても波及が小さい。
2. **#1 顔クラスタ後処理の残り**（構造 34・依然として最大）— ADR-198 で種の構築・名前追随・
   ノブは純ロジックへ出したが、**`+Edit` / `+Undo` / `+Review` / `+Absorb` が同じ行を別経路で
   書く**構造は手つかず（状態 164・結合 24）。ここは**次に顔の精度改善をするときについでに**。
3. **#3 家族共有 / #8 バックアップ**（構造 22 / 17）— 複雑さの多くが外部仕様由来で、
   構造を直しても仕様は残る。**費用対効果が低い**。
4. **#9 DropboxPhotoStore**（結合 50 が最大・確度 0.62）— **やらない方がよい**。

### ADR-198 で分かった、次に活かすこと

- **「手続きを純ロジックへ出す」で減るのは、可変状態と分岐とテストの薄さ**。結合とマーク密度は
  減らない（第 3 回の実測: 顔クラスタ後処理で状態 176→164・分岐 61→46 だが結合 23→24・
  マーク密度は据え置き）。**結合を減らしたいなら型を分けるしかなく、それは別の作業**。
- **断面プロトコルは結合数を減らさない**。減るのは「読み手が追う範囲」だけ。指標には出ない。
- **⚠️ SwiftUI のビューに断面プロトコルを渡さない**。`@Observable` の追従は具象型でしか効かず、
  プロトコル越しに読むと再描画されない（ADR-198）。

**やらない方がよいもの**: #9 DropboxPhotoStore（確度 0.62・結合 50）、#3 家族共有と
#8 バックアップ（複雑さの多くが外部仕様由来で、構造を直しても仕様は残る）。
