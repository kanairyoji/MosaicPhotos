## 途中終了すると成功済み写真のメタデータが失われる

- 箇所: `Packages/BackupKit/Sources/BackupKit/BackupRunner.swift:0`
- 分類:  /  / local
- 検討した回数: 1（初出 2026-08-26）
- 症状: 写真本体はバックアップ済みになる一方、人物・アルバム・位置・お気に入り等のメタデータが Dropbox に残らず、再インストールや機種変更後に復元できない。
- 退けた方向:
  - 方向は正しいが、レコード保存の完了後にジャーナルへ追記する順序では、runnerSaveRecord の完了と追記の間にキャンセル・プロセス終了が起きると、完了済みレコードだけが残ってメタデータを失う。計画自身も「最大1件しか落ちない」としており、「成功済み全写真」を要求する条件1・2を満たさない。メタデータを永続的な再送待ちへ先に記録し、その永続化完了後に完了レコードを保存する順序に変更し、リモート反映が確認されるまでキューから削除しないこと。pending が空でもキューをドレインする変更は条件3を満たせる。

## 検証後の変更を見ずに端末写真を削除する

- 箇所: `Packages/BackupKit/Sources/BackupKit/OffloadService.swift:0`
- 分類:  /  / design
- 検討した回数: 1（初出 2026-08-26）
- 症状: 検証後に編集された写真、または検証後にクラウド側の同一コピーが失われた写真を端末から削除し、最新データを失う可能性がある。
- 退けた方向:
  - 再検査を台帳書き込み直前に置くだけでは、再検査後の台帳保存中および PhotoKit の確認ダイアログ中に発生した端末編集・置換や Dropbox 実体の削除・置換を検出できません。deferredCriteria が明示的に除外しているのは条件1の厳密な瞬間一致だけですが、同じ窓により未延期の条件2・3も満たせません。また、modificationDate が非 nil の対象でバイト列を再取得しないため、日付が変わらない置換も条件2上は見逃します。実現不能な PhotoKit の原子的 compare-and-delete が前提なら、条件1だけでなく、再検査後から削除確定までに起きる変更に関する条件2・3も deferredCriteria に明記してください。条件2の非延期部分を満たすには、最終再検査で全対象の現行バイト列を再ロードして hash・サイズを比較し、modificationDate は補助信号として扱う必要があります。

## メンバー更新中のコピーが除外写真を復活させる

- 箇所: `Packages/BackupKit/Sources/BackupKit/Share/ShareSyncEngine.swift:0`
- 分類:  /  / local
- 検討した回数: 1（初出 2026-08-26）
- 症状: 「今の内容に更新」または同じ共有セットの再共有で外した写真が、共有先の Dropbox フォルダに残り続ける。ローカル記録には存在しないため、その後も通常の反映では管理・削除できない。
- 退けた方向:
  - 更新処理の排他化、コピー発行前の宛先記録、パス墓標による再削除は正しい方向。ただし墓標を有限の猶予時間だけ保持すると、その猶予後にサーバー側コピージョブが完了した場合、除外ファイルが最終状態に残り、申告されていない条件2を満たせない。発行した非同期ジョブを終端状態まで追跡し、完了後に最終削除と不在確認を行うまで墓標を消さない設計にすること。終端を確認できないジョブについては墓標を永続保持し、以後の反映でも削除・不在確認を継続する必要がある。条件3のサイドカー遅延と条件4の一時生成はdeferredCriteriaとして申告済みなので、それ自体は判定上の不足ではない。

## 旧アカウントの遅延ダウンロードが新キャッシュへ入る

- 箇所: `Packages/DropboxCore/Sources/DropboxCore/Store/DropboxPhotoStore+Images.swift:0`
- 分類:  /  / design / 優先度 P2
- 検討した回数: 1（初出 2026-08-26）
- 症状: アカウント切替後、同じ Dropbox パスにある写真のサムネイルやフル画像として、切替前アカウントの画像が表示される。
- 退けた方向:
  - 開始時トークンと表示前検証の方向は正しいが、書込マーカーだけでは条件3を保証できない。Aが書込前検証を通過した後にBが保存し、その後Aのディスク書込が完了すると、AはBのファイルを上書きできる。Aの finalize がマーカー不一致で削除を控えても、内容はAのまま残る。パス単位で「検証→書込→確定」を直列化するか、一意な一時ファイルへ書いた後、最新トークンと所有権を検証した処理だけが原子的に公開できる方式へ変更する必要がある。また、画像の検証はダウンロード直後ではなく、デコードなど全 suspension の後、return／deliver の直前にも行うこと。サムネイルでは旧Aの inFlight と待機者がアカウント切替後もパスだけで共有されるため、Bの同一パス要求がAへ合流し、Aの nil 配送でBの待機者まで終了し得る。切替時にバッチ状態をリセットするか、取得・inFlight・待機者をキャッシュ世代で分離し、旧世代の結果が新世代の待機者へ配送されないよう計画へ追加すれば条件1〜4を満たせる。

## 同名の別人物は再スキャン移行で片方の名前を失う

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/FaceStore+Rebuild.swift:315`
- 分類: dataLoss / firstRunOrMigration / local / 優先度 P1
- 検討した回数: 1（初出 2026-09-02）
- 症状: 同じ名前を付けた別々の人物がいると、顔モデルやパイプラインの版上げ後に一方だけが命名され、もう一方の名前と写真との対応記録が失われる。
- 解決と言える条件:
  - 異なる旧人物に同じ表示名が付いていても、各エントリが写真キーの重なりに対応する別々の新人物へ再適用される。
  - 同名クラスタが既に存在するだけでは、写真キーが対応しない別エントリが消化済みにならない。
  - まだ対応先を確定できないエントリは、同名クラスタの有無にかかわらず後続スキャンで再評価できる状態に残る。
  - 全エントリが適用済みまたは明示された期限切れになるまで、名前と旧メンバー写真キーの対応が失われない。
- 退けた方向:
  - 方向は正しいですが、2点修正が必要です。まず、既に同名のクラスタを手順 (iii) で先に適用済み・予約にすると、処理順によって本来そのクラスタにしか対応できない別エントリを締め出せます。同名か無名かは書き込み要否の違いとして扱い、すべての候補を同一の一対一割り当てに含めてください。また、重なり降順の貪欲法でも、局所的な最大ペアが別エントリ唯一の対応先を奪い、存在する一対一対応を見逃す場合があります。最大対応数を優先し、その中で総重なりを最大化する二部マッチング等にし、曖昧性も割り当て全体について判定する必要があります。次に、連続した版上げで併合対象を「未適用の旧エントリ」だけにすると、まだ未適用エントリが残っている間に適用済みエントリの appliedClusterID 予約と旧 memberRefKeys が失われます。その結果、未適用の同名エントリが以前の対応先へ吸い込まれ得ます。持ち越し全体が解決または期限切れになるまでは、検証可能な適用済みエントリも予約情報とともに併合・保持してください。
