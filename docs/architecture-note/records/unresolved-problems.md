# 未解決の課題（直し方に設計判断が要る）

**実在する問題**だが、どう直すかの合意に至っていないもの。
素直な修正案は検討して退けてある（下の「退けた方向」）。片付けるには、
多くの場合コードの局所修正ではなく**設計上の選択**が要る。

片付いたら、この一覧から消して `decisions.md` / `case-studies.md` へ移すこと。

## 「アプリを離れても解析を続ける」トグルが片道でしか効かない

- 箇所: `MosaicPhotos/AnalysisSession.swift:82-92`（setter が `!newValue` しか扱わない）と
  `:95-102`（`downgradeToForegroundOnly`）
- 分類: settingIneffective / 優先度 P2（初出 2026-09-20・レビューループ 2 周目）
- 症状:
  1. **戻せない**: 走行中に OFF → 前面のみモードへ降りる。そのあと ON に戻しても
     `mode` は `.foregroundOnly` のままなので、アプリを離れると解析が止まる。
     設定は「離れても続ける」と表示しているのに止まる＝表示と挙動が逆。
  2. **消したはずの表示が出る**: `submitContinuedTask()` は `BGTaskScheduler.submit` の
     成功で `.continued` にするが、`self.task` は OS がハンドラを呼ぶまで nil。
     その窓で OFF にすると `downgradeToForegroundOnly` は降ろすものが無く、
     `BGTaskScheduler.cancel` も呼ばれない。あとから OS がタスクを渡すと `attach` が受け取り、
     ロック画面と Dynamic Island のインジケータが出る——消すために OFF にしたのに。
- なぜ設計判断が要るか: 1 は「ON に戻したら継続タスクを取り直す」で直りそうに見えるが、
  BGTask の再 submit は OS の裁量で、走行中に何度も submit/cancel を繰り返す挙動は
  実機でしか確かめられない。2 は `BGTaskScheduler.cancel(taskRequestWithIdentifier:)` を
  足すだけに見えるが、`attach` 側でも「いま継続モードを望んでいるか」を見ないと
  競合は残る。どちらも**実機で確かめてから**入れるべき種類の変更。
- 補足: この経路は 1 周目の修正（トグルをセッションに通す）で**初めて到達可能**になった。
  それまで setter は一度も呼ばれていなかったので、症状は存在しなかった。

## 全画面で開いている最中に一覧が並び替わると、ラベルと中身が食い違う

- 箇所: `Packages/PhotoSourceKit/Sources/PhotoSourceKit/Views/PhotoPageView.swift`
  （`windowItems` / `windowLowerBound` / `recenterWindowIfNeeded`）
- 分類: staleUI / 優先度 P2（初出 2026-09-20・レビューループ 8〜9 周目）
- 症状: 写真を全画面で開いている最中に一覧が並び替わると、上部ラベルと情報パネルは
  **選んでいる写真**の値を出すのに、めくられている中身は**別の写真**になる。
  次にスワイプするまで直らない。ADR-199（受け取った撮影日の反映）で写真が列の末尾
  （アップロード順の位置）から中ほど（撮影日の位置）へ動く、がまさにこの形。
- 原因: 全 8.6 万件を `TabView` に渡さず中央±30 のウィンドウだけを切り出す。その位置を
  寄せ直す `recenterWindowIfNeeded` の呼び出し口は `onChange(of: currentID)` だけで、
  **並び替えは `currentID` を変えない**。
- **退けた方向（8 周目で入れて 9 周目で撤回）**: 「`currentIndex` と `currentID` がズレたら
  並び替わった合図」として検知する。`currentIndex` はその `onChange` の中でしか更新されないので
  `currentID` に 1 パス遅れ、**ズレはめくるたびに必ず真**になる。そこで位置を引き直すと、
  外れた当たりで `PagingIndex.resolve` が全件走査に落ち、1 回のスワイプで 2 度の線形探索
  （各要素で `PHAsset.localIdentifier` を読む）が走る——18 秒のハング（diagnostics-58）を
  作った経路そのもの。**稀な表示の乱れを、確実な性能退行と交換してはいけない。**
- 解決と言える条件:
  - 一覧が並び替わったときにウィンドウが選択中の写真を含むよう寄せ直される。
  - **ふつうのスワイプでは 1 件も余計に走査しない**（`PagingIndex` の当たりが効き続ける）。
- 検討した方向:
  - (a) ストアに「中身の版」を持たせ（`MergedPhotoStore` は既に指紋を計算している）、
    `PhotoStore` プロトコルへ既定値つきで足して `onChange(of: store.contentVersion)` で拾う。
    正確で O(1)。ただしプロトコルを触るので、他のストアの実装方針も決める必要がある。
  - (b) `windowItems` の中で「窓が `currentID` を含むか」を毎回見る（窓の幅ぶん＝61 件の走査）。
    状態を持たずに済むが、計算プロパティなので**並び替え後は毎パス全件走査**に落ちる。
  - どちらを採るかは、`PhotoStore` プロトコルに表示以外の関心事（中身の版）を持たせてよいかの判断。

## 再クラスタ後の「重心へ寄与したか」の記録が実際の計算と食い違う

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/FaceStore+Rebuild.swift:154-157`（書き戻し）と
  `FaceSeedBuilder.swift:149`（種の計算）
- 分類: dataLoss / 優先度 **P1**（初出 2026-09-20・レビューループ 10 周目）
- 症状（推定・実機未確認）: 名前や確認顔を持つ人物から写真を数枚外すと、
  **人物の重心が壊れる**か、**行ごと消えて人物が一覧から居なくなる**。
- 原因: 種を作るとき、ピン留めしたメンバーのうち**品質フロアを満たすものだけ**を
  `sum`/`count` に足している（`guard member.contributes(qualityFloor:) else { continue }`）。
  ところが書き戻しは `pinnedCluster[f.faceID] != nil || quality >= floor` で、
  **ピン留めなら品質に関係なく「寄与した」と記録する**。実ライブラリの顔は約半分が
  フロア未満（`FaceStore+People.swift:13-15`）なので、30 枚の人物で `count == 4` なのに
  30 行が「寄与した」と言う状態になる。
  あとで写真を外すと 1 枚ごとに単位ベクトルを引き `count` を減らすので、
  4 枚外したところで `count` が尽きる（`FaceClustering.removing` の `count > 1` ガード）。
  - 名前/代表顔/束ねがある → `sum` が零ベクトルになり、次の再クラスタまで誰も合流しない。
  - **確認顔だけの無名クラスタ** → `isUserClaimed` は `confirmedAt` を見ないので**行が消える**。
    残った顔は孤児になり、`repairOrphanFaces` が未割り当てへ戻す＝人物が消える。
  - 種のピン留めが全員フロア未満だと `count = max(1, count)` で 1 になり、**最初の 1 枚で消える**。
- なぜ設計判断が要るか: 素直に書き戻しを `quality >= floor` だけにすると計算とは揃うが、
  `contributes` は `contributesToCentroid ?? (quality >= qualityFloor)` なので、
  既存行の値が次の判断に効く（自己参照）。どの時点の値を正とするか＝
  「寄与したか」を**事実の記録**とするか**方針の再評価**とするかの選択が要る。
  併せて `isUserClaimed` に `confirmedAt` を含めるかも決める必要がある
  （確認顔は ADR-132 の言う「ユーザーの表明」なのに、行の保護対象に入っていない）。
- 補足: `contributesToCentroid` に触れるテストは fixture 用の 1 か所だけ。

## 再クラスタで無名クラスタの ID が毎晩変わり、ピープルグループが黙って欠ける

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/FaceStore+Rebuild.swift:165-168`
- 分類: dataLoss / 優先度 P2（初出 2026-09-20・レビューループ 10 周目）
- 症状（推定・実機未確認）: 家族のピープルグループに無名の人物（「Person 12」など）を入れると、
  次の再クラスタでその人がグループから**黙って消える**。共有フォルダからもその人の写真が消える。
- 原因: 種になるのは「名前・確認顔・代表顔・**束ね（`personGroupID`）**」を持つクラスタだけ。
  `PeopleGroupRecord`（ユーザーが作ったピープルグループ）のメンバーであることは**種の条件に入っていない**
  ——`personGroupID`（同じ子を束ねる）とは別の概念。種でないクラスタは行ごと消え、
  顔は新しい ID へ割り当て直される。`remapPeopleGroups` は手動の統合からしか呼ばれず、
  `PeopleGroupInfo.resolve` は解決できないメンバーを黙って落とす。
- なぜ設計判断が要るか: 素直な修正は「グループのメンバーも種にする」だが、
  それは**無名のクラスタを機械の再編から守る**ことを意味し、ADR-132 の適用範囲を広げる判断になる。
  代わりに再クラスタ後に ID を付け替える（`remapPeopleGroups` を呼ぶ）道もあるが、
  無名クラスタは分裂・統合もするので 1 対 1 に対応しない。

## パイプライン版を上げると束ねとピープルグループが失われる

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/PeopleEngine.swift:424-436`
- 分類: dataLoss / 優先度 P2（初出 2026-09-20・レビューループ 10 周目）
- 症状（推定・実機未確認）: 顔パイプラインの版を上げて再スキャンすると、名前は持ち越されるが、
  **子どもの束ね（ADR-61/134）は解けて別人に戻り**、ピープルグループは中身が空になる。
- 原因: 持ち越しの荷物（`NameCarryover.Entry`）が `name` と `memberRefKeys` だけで、
  `personGroupID` を含まない。`store.reset()` は `PeopleGroupRecord` を消さないので、
  記録は残るが指している ID が二度と解決しない。
  モデル世代の切り替え（`promoteShadow`）は名前でグループを組み直すが、束ねの再現は無い。
- なぜ設計判断が要るか: 束ねは「この 2 つのクラスタは同じ人」という表明で、
  再スキャン後のクラスタとの対応づけが要る。名前と同じ「写真の重なり」で寄せるのか、
  束ねだけ別の持ち越し方にするのかを決める必要がある。

## モデル世代の切り替えが `@Model` をアクターの外で読む

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/PeopleEngine+Generation.swift:58,61`
- 分類: concurrency / 優先度 P2（初出 2026-09-20・レビューループ 10 周目）

## クラウド一覧の反映が古いまま固定され、何も直しに来ない

- 箇所: `Packages/DropboxCore/Sources/DropboxCore/Store/DropboxPhotoStore.swift`
  （`reflectCachedItems` の合流・`clearAll` が `itemsRevision` を進めない・
  同期ルート変更の枝が `loadGeneration` を進めない）
- 分類: staleUI / 優先度 P1（初出 2026-09-20・レビューループ 16 周目）
- 症状（推定・実機未確認）:
  1. 初回同期の直後、**Dropbox 側で消した写真が一覧に残り続ける**（タップしても開けない）。
     ポーリングは静かなので誰も直しに来ず、画面に入り直しても直らない
     （中身があると再読込を飛ばすため）。アプリを開き直すまで残る。
  2. 保存先フォルダを変えたとき、**古いフォルダの写真が出たまま**になる（新しいフォルダが
     空だと永久に）。
- 原因: 反映処理は「同じ口座なら走行中のものに合流する」が、**合流先が読んだ時点の
  スナップショット**を返す。しかも走行中の目印は所有者が起こされるまで消えないので、
  **既に終わったものへ合流**して即座に古い件数が返ることがある。
  合流された側が最後に「この版まで反映した」と記録するため、次回の反映も飛ばされる。
  併せて、全消去が版を進めない・ルート変更の枝が世代を進めないので、
  古い配列を後から書き戻す経路が残っている。
- なぜ設計判断が要るか: 合流をやめれば（毎回やり直す）正しいが、
  初回同期中は 0.4 秒ごとに反映が走る設計なので、6.8 万件の取り出しが重なる。
  「合流してよいのは、合流先が自分より新しい版を読んでいるときだけ」という条件を
  どう表現するか（版を持たせる／走行中の目印に版を添える）を決める必要がある。
  ⚠️ **この判断はレビュー 12〜14 周目と同じ形**（「誰が最後に書いたか」で決める）。
  同じ道具立てで解けるはず。

## キャッシュを消しても使用量の集計が残り、共有の容量予算が詰まる

- 箇所: `Packages/DropboxCore/Sources/DropboxCore/Cache/DropboxCacheStore+Eviction.swift`（`clearAll`）
- 分類: budgetJam / 優先度 P2（初出 2026-09-20・レビューループ 16 周目）
- 症状（推定・実機未確認）: Developer Options の「キャッシュを消す」を押しても、
  設定の使用量表示が減らない（アプリを開き直すまで）。さらに、**容量予算の掃除が
  その回以降まったく効かなくなる**——幻の使用量を持つ参加者が毎回「いちばん捨てるべき」と
  選ばれ、実際には捨てるものが無いので 0 件を返し、掃除のループがそこで止まる。
  端末サムネや顔アバターのキャッシュが予算を超えても縮まない。
- 原因: 全消去は使用量の台帳（行）を消すが、**メモリ上の集計**を消していない。
  読み直しのフラグも立ったままなので二度と読み直さない。
- なぜ設計判断が要るか: 素直に集計を 0 にすればよいが、予算の参加者は複数あり、
  「消した」をどう他の参加者へ伝えるか（再計算を促すか、各自が持つか）の取り決めが要る。

## 先読みの取り消しが効かず、画面外の写真を取りに行く

- 箇所: `Packages/DropboxCore/Sources/DropboxCore/Store/DropboxThumbnailBatcher.swift`
- 分類: waste / 優先度 P2（初出 2026-09-20・レビューループ 16 周目）
- 症状: スクラブ中に、画面外へ流れた写真のサムネを取りに行く。回線ポリシーの判定は
  先読みの入口でしか見ないので、**セルラーでも**取りに行く。
- 原因: 先読みの登録は非同期（1 件ずつキャッシュの有無を聞くため）なのに、
  取り消しは同期で走る。取り消しの時点ではまだ登録されていないので何も消せず、
  そのあと登録が進む。
- なぜ設計判断が要るか: 取り消しを非同期にする・登録前に取り消し済みを記録する・
  登録をまとめて 1 往復にする、のどれかを選ぶ。3 つ目が筋は良いが、
  キャッシュの有無を一括で聞く口が要る。

## クラウド写真の撮影日は、一覧からは**取れない**（API 仕様）

- 箇所: `Packages/DropboxCore/Sources/DropboxCore/Sync/DeltaPageParser.swift`（`timeTaken ?? modified`）
- 分類: dataQuality / 優先度 P1（初出 2026-09-20・レビューループ 17 周目）
- **⚠️ 16 周目にここへ書いた「同期カーソルに `include_media_info` が無いのが根」は誤りだった。**
  17 周目のレビューが一次情報を示し、こちらで Dropbox 公式 SDK の記述を確認した:
  > This field will not be set on entries returned by `list_folder`,
  > `list_folder_continue`, or `get_thumbnail_batch`, **starting December 2, 2019**.
  つまり `include_media_info` を付けても**一覧系では無視される**。
  16 周目の修正は無効（無害なので引数は外し、事実をコメントに残した）。
  当時書いた対処案（全件再スキャン）は**何も直さない**ので撤回する。
- 事実関係:
  - クラウド写真の `captureDate` は、同期経路では**常に** `client_modified`
    （＝ファイルの更新時刻。アプリがバックアップした写真では撮影日と一致するが、
    他端末のカメラアップロードや Dropbox 側での追加では**アップロード時刻**）。
  - `media_info`（撮影日時・撮影地）が取れる唯一の口は `files/get_metadata`。
    撮影地はそこから 1 枚ずつ取っている（`DropboxPhotoStore+Location`・4〜6 秒／枚）。
    撮影日は同じ経路を使っていない。
- **これまでの対処の位置づけが変わる**: ADR-128（バックアップ台帳の撮影日で上書き）と
  ADR-199（共有は解析データで撮影日を渡す）は「症状への手当て」ではなく、
  **データを返さない API に対する正しい設計**だった。台帳にも解析データにも載らない写真
  （他端末のカメラアップロード・Dropbox 側での追加）だけが残る。
- 解決と言える条件: 台帳にも解析データにも載らないクラウド写真でも、撮影日が EXIF のものになる。
- 検討した方向:
  - (a) 撮影地と同じく `files/get_metadata` で 1 枚ずつ遅延取得し、キャッシュへ書き戻す。
    ⚠️ 6.8 万枚に対して 1 枚 4〜6 秒は現実的でない。**見えている写真だけ**取りに行く

## 【P0 相当・実機確認を最優先】オフロードの印が誰も読まない場所へ書かれている

- 箇所: `Packages/BackupKit/Sources/BackupKit/OffloadService.swift:360-364`（`folderByPath`）
- 分類: dataLoss / 優先度 **P0**（初出 2026-09-20・レビューループ 15 周目）
- 症状（推定・**実機で最優先に確かめること**）: オフロード（端末の原本を消して Dropbox だけに残す）
  した写真が、**機種変更・再インストール後に取り戻せない**。
  台帳が空のときに `offloadedAt` の印から再構築する経路（ADR-39/40）が、印を 1 件も見つけられない。
  利用者から見ると「Photos で消した写真」と区別が付かず、端末アルバムの合成にも出てこない。
- 原因: 印を書くフォルダを**写真のパスの親**から作っている。
  ADR-176 で写真は `<backupRoot>/<YYYY>/<YYYY-MM>/` に置かれるようになったので、
  親は**月のフォルダ**であって `backupRoot` ではない。
  - 印の書き先: `<root>/<YYYY>/<YYYY-MM>/.mosaic/meta/<shard>.json`（新規に作られる）
  - アップロード時の本来の書き先: `<root>/.mosaic/meta/<shard>.json`（`BackupRunner` は `folder` を渡す）
  - 読む側: `<設定のフォルダ>` と `<端末のバックアップルート>` の下しか見ない（`HomeView`）
  書いた直後に成功が返るので**印は「送信済み」と記録され、二度と書き直されない**。
  コメントの前提（「バックアップフォルダ直下前提」）が ADR-176 で成り立たなくなったまま残っている。
- 影響範囲: **ADR-176 以降にオフロードした写真すべて**。既にオフロード済みの利用者は、
  いま手を打たないと機種変更時に失う。
- なぜ設計判断が要るか（直し方の候補）:
  - (a) 写真のパスからバックアップルートを復元する（`/YYYY/YYYY-MM` または `/undated` を剥がす）。
    ⚠️ 旧レイアウト（フラット）と端末フォルダ、保存先変更の前後が混ざるので、
    「剥がしてよい形か」の判定が要る。コメントが警告している事故（別フォルダのエントリを
    1 つのシャードへ書き、全件を送信済みにする）を再発させない形で書く必要がある。
  - (b) 印を書く側に `backupRoot` を渡す（呼び出し側は知っている）。
    素直だが、`OffloadMarkerTarget` に根を持たせるか引数を増やすかの選択になる。
  - (c) 既に誤った場所へ書かれた印の**救済**をどうするか。`markerUploadedAt` が立っているので
    再送されない。版を上げて 1 度だけ送り直す仕組み（ADR-199 の受信能力の版と同じ形）が要る。
  - テストが前提を守れていない: `OffloadSafetyTests` は平らなパス（`/backup/a.jpg`）を使っており、
    ADR-176 のレイアウトを一度も通していない。直すときは**月フォルダのパス**で固定する。

## メタデータの控えが、背景アップロードの書き込みごと消される

- 箇所: `Packages/BackupKit/Sources/BackupKit/BackupRunner.swift:571`（`load()`）と
  `:609-610`（`save` → `clearJournal`）、`BackupEngine+Settle.swift:18`（`appendEntry`）
- 分類: dataLoss / 優先度 P1（初出 2026-09-20・レビューループ 15 周目）
- 症状（推定・実機未確認）: 夜間のバックアップで上がった写真の一部について、
  **人物名・アルバム・位置情報・お気に入り**が Dropbox 側のメタデータに載らない。
  その写真には完了記録が付くので、二度と作り直されない。
- 原因: `writeMetadata` は控えを**読んだ時点のスナップショット**で処理し、最後に
  `clearJournal()` で**ファイルごと**消す。その間も背景アップロードの完了通知は届き続け、
  完了ごとに控えへ 1 行追記される（ADR-171 の「完了記録より先に控えを書く」は守られている）。
  スナップショットに無いその行が、ファイルごと消される。
- なぜ設計判断が要るか: 素直な修正は「消すのでなく、読んだ行だけ消す」だが、
  控えは追記専用の行ファイルで、行単位の削除には読み直し＋書き直しが要る
  （その間にまた追記される）。世代を付ける・別ファイルへ移してから処理する等、
  取り扱いの形そのものを決める必要がある。

## 控えの送信が二重になり、送りっぱなしで溜まり続ける

## 窓を畳んだ後に、顔の仕上げ処理が走り出す

- 箇所: `Packages/FaceCore/Sources/FaceCore/Faces/PeopleEngine.swift` の
  `scan.start` 本体の末尾（`reapplyCarryoverNames` / `rebuildClustersIfNeeded` /
  `promoteShadowIfReady`）
- 分類: osCitizenship / 優先度 P2（初出 2026-09-20・レビューループ 11 周目、13 周目で整理）
- 症状（推定・実機未確認）: 処理枠の期限切れは「顔スキャンを止める → OS に完了を告げる」の
  順で走る。顔スキャンの本体は取り消しを受けると**正常に返る**ので、その後ろの仕上げ
  （名前の貼り直し → 全再クラスタ → **モデル世代の切り替え**）へそのまま流れ込む。
  その時点では背面・充電・アイドルなので譲りの判定も通る。つまり**OS に終わったと告げた後で
  全再クラスタが始まり**、書き込みの途中でプロセスを吊るされ得る。
  前面復帰でも、譲ってほしい場面で世代の切り替えまで走る。
- **退けた方向（11 周目で入れて 13 周目で撤回）**: 末尾に `guard !Task.isCancelled else { return }`
  を置く。これは**逆転を生む**——残作業が窓 1 回で終わらない限り、進んだ夜は必ず
  期限切れ＝取り消しで終わるので、仕上げは「何も進まなかった夜」にしか走らなくなる。
  版上げ後の名前の段階的な復元も、修正を全体へ広げる夜間の自己修復（ADR-46 B2）も、
  **進んだ夜には一度も走らない**。稀な行儀の問題を、機能の停止と交換してしまう
  （レビュー 9 周目と同じ誤り）。
- 解決と言える条件:
  - 名前の復元と夜間の自己修復は、**進んだ夜にも走る**。
  - OS に完了を告げた後に、新しい重い処理を**始めない**。
- 検討した方向:
  - (a) 仕上げを窓の**前半**へ移す（スキャンの前に回す）。順序が変わるので、
    どれを先にするかは夜間の枠配分の判断になる。
  - (b) 仕上げを中断・再開できる形にする（`rebuildClusters` を分割可能にする）。
    ADR-46 の制約付き再クラスタは全体を一度に見る前提なので、分割の意味づけが要る。
  - (c) 期限切れのときだけ仕上げを飛ばす（前面復帰では走らせる）。
    期限切れかどうかを顔側が知る必要があり、停止の伝え方を変えることになる。

## AI アルバム: 増分評価が全評価と違う規則で動いている（6 件）

レビュー 16 周目。**アルバムの中身が変わる指摘は、このプロジェクトでは
クエリ集ハーネスの計測で決める規則**（CLAUDE.md）なので、直さず並べる。
直すときは `search-quality.md` の両ハーネスを回して差分を台帳へ記すこと。

1. **採点できないアルバムが、新しい写真を永久に溜め続ける。** 採点の一時的な失敗のために
   用意した「持ち越し」が、**恒久的な失敗**（訳文が空＝Apple Intelligence の無い端末で
   除外だけのクエリ）でも使われる。5 分ごとに全件を積み直し、そのたびに
   数万件ぶんのベクトルを取り出す（ADR-119/122 の形）。
2. **増分評価がシーンタグの除外を適用していない。** 全評価は「除外語にタグが当たったら落とす」
   が、増分にはその段が無い。「犬が写っていない写真」に犬の写真が入り、次の全評価まで残る。
3. **増分評価が根拠ゲートと審査を飛ばす**枝がある（ハード条件だけのアルバム）。
   全評価では通らない写真が入り、次の全評価で消える＝データが変わっていないのに中身が動く。
4. **上限（既定 50 件）が増分では効かない。** 全評価のたびに 50 件へ戻るが、
   その間は増分で増え続ける（100 → 150…）。
5. **`refresh` が確定前のアルバムで LLM を走らせ、確定済みにしてしまう。** ADR-23 の
   「解釈は作成時 1 回」に反する。しかも空振りしたときの再挑戦は確定処理の中にしか無いので、
   **空のままのアルバムが永久に空**になる。
6. **除外だけのクエリが、作成時に全ライブラリのアルバムを作る。** Apple Intelligence の
   ある端末では数秒後に上書きされるが、無い端末では 3 万件のアルバムが最終状態になる
   （1 と重なると二度と直らない）。

併せて、アルバムのループの中で毎回タグ台帳・OCR・人数の**全件**を読み直しており
（アルバム 5 本で 8.6 万行 × 10 回）、`HeavyLoad` の申告も無い（CLAUDE.md の規則）。
こちらは中身を変えないので、手を入れてよい部類。

## 解析の完了判定が「止められている」を「終わった」と言い得る

- 箇所: `MosaicPhotos/AnalysisSession.swift:268`（`faces = people.isScanning ? people.remaining : 0`）

## 顔の精度ハーネスの 2 指標が非決定的（2026-09-19・ADR-198 で判明）
- 症状: 同じコードで `FaceAccuracyEvalTests` を回しても、**「純度<0.8 の人数」と
  「レビュー候補の当たり数・拾えた分裂 %」が実行ごとに ±1 揺れる**（6 実行で確認）。
  中核指標（B3 の P/R/F1・pair F1・クラスタ数・分裂）は全ペアで完全一致。
- 影響: 「構造変更で数値が動いたら中止」というゲートが、この 2 指標にはそのまま使えない。
  実際に 1 度「退行か」と読み違え、変更前どうしを突き合わせて初めてノイズと分かった。
- 原因（推定・未確認）: 同数・同値で並んだときの順序。Swift の `Dictionary` / `Set` の
  反復順序はプロセスごとのハッシュシードで変わる。どこで拾っているかは特定していない。
- 対処: `face-accuracy.md` に「どの指標が決定的か」の表を書いた（比較は中核指標で行う）。
  根治するなら、境界カウントの集計を配列の安定ソート経由にする。
- 関連: `face-accuracy.md` / ADR-119（フレーキーなテストはバグを隠す）/ ADR-198。
