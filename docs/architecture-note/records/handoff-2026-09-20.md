## 1. まず決めていただきたい 3 件

### (1) オフロードの印が誰も読まない場所へ書かれている 【P0・写真が失われる】
- オフロード＝端末の原本を消して Dropbox だけに残す機能。その「印」が、
  写真の置き場所が年月フォルダになった（ADR-176）以降、**月フォルダの下**へ書かれている。
  読む側はバックアップルートの下しか見ない。しかもカタログにも登録しないので**二重に届かない**。
- 書いた直後に成功が返るので「送信済み」と記録され、**二度と書き直されない**。
- 帰結: **既にオフロードした写真が、機種変更・再インストールで取り戻せない。**
- **確かめ方は 1 分**: Dropbox で `<バックアップルート>/.mosaic/meta/<年-月>.json` を開き、
  オフロードした写真の `offloadedAt` があるか見る（`device-verification.md` の Z1）。
- 直し方の選択肢 3 つ＋既に誤って書かれた印の救済を `unresolved-problems.md` に記載。
- **私の判断で触らなかった理由**: 影響が「利用者の写真」で、直し方に選択肢があるため。

### (2) クラウド写真の撮影日をどうするか 【P1】
- Dropbox は **2019-12-02 以降、一覧系 API で撮影日時（`media_info`）を返さない**（一次情報で確認）。
  したがってクラウド写真の日付は**常にアップロード時刻**になる。
- ADR-128（台帳で上書き）と ADR-199（共有は解析データで渡す）は、この API 制約に対する
  **正しい対処**だった。残るのは台帳にも解析データにも載らない写真
  （他端末のカメラアップロード・Dropbox 側での追加）。
- 選択肢: (a) 撮影地と同じく 1 枚ずつ遅延取得（4〜6 秒／枚・並びが動く懸念）、
  (b) まとめて引く口を作る（レート制限との兼ね合い）、(c) 仕様と割り切って明記。
- ⚠️ **16 周目に「根を見つけた」と報告したのは誤り**でした。17・18 周目で訂正済み。

### (3) 顔の「重心へ寄与したか」の記録が計算と食い違う 【P1・人物が消える】
- 種を作るときは品質フロアを満たす顔だけを重心に足すのに、書き戻しは
  「ピン留めなら寄与した」と記録する。実ライブラリの顔は**約半分がフロア未満**（実測 48%）。
- 帰結: 写真を数枚外すと重心が零ベクトルになるか、**人物の行ごと消える**。
- 直すと自己参照になる（`contributes` が自分の記録を読む）ので、
  「寄与したか」を事実の記録とするか方針の再評価とするかの選択が要る。

## 4. このループで繰り返した誤りの型（次に同じことをしないために）

`case-studies.md` に事例として残した。特に効きそうなもの:

1. **値だけが直る更新は、識別子を見る仕組みを全部すり抜ける。** 層を変えて三度現れた。
2. **再試行や上限を足すときは、やり直しても解決しない失敗と分け、系が前へ進むか確かめる。**
3. **状態の復元は「値」ではなく「誰が最後に書いたか」で決める。** 3 周かけて収束した。
4. **稀な不具合を、確実な性能退行や機能の停止と交換しない。** 二度踏んで二度撤回した。
5. **同じ規則を必要とする場所を、修正の前に数える。** 記録の訂正にも当てはまる。
6. **外部 API の挙動を、コードの読みだけで断定しない。** 3 回やった。
7. **レビューの対象を固定すると、見つかる欠陥の質が落ちる。** 周回数ではなく被覆で決まる。
