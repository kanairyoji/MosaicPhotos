規約とテスト方針

コードベースの一貫性を保つための約束と、2 系統のテストの回し方。

コーディング規約（抜粋）

  • 状態管理: @Observable のみ。ObservableObject/Combine は使わない。
  • 並行性: アプリは既定 @MainActor。バックグラウンドのコールバックは Task { @MainActor in } で戻す。
  • 設定キーの一元化: @AppStorage/UserDefaults のキーは各パッケージの専用 enum に集約（GridSettingsKeys / CacheSettingsKeys / DropboxCacheSettingsKeys / BackupSettingsKeys / AutoAlbumSettingsKeys / アプリ層は AppSettingsKeys）。
  • ロギングの一元化: MosaicSupport.LogChannel に集約。error は常時、info/verbose は DEBUG のみ。各レベルは診断ログにも転記。
  • DI seam: 外部依存はプロトコル化しデフォルト引数で本番実装を注入（HTTPClient / DateProvider / AccessTokenProvider）。
  • UI 文言は英語: 表示文字列は英語でハードコードしない方針（国際リリース前提）。コメント・コミットは日本語可。
  • 文字コード: ソース・API ボディ・Keychain 値はすべて UTF-8。
  • 機密の非保存: クレデンシャル・トークン・APIキーをファイルやログに書かない。

⚠️ 機械で守る規約（CI ブロッキング）

規約を文章で書くだけでは守られない——というのが、この台帳で最多の不具合の形だった。 「同じ規則が複数の場所に散っていて、1 か所だけ抜けている」を 2026-09 以降に数え始めたら 11 例あった。そこで「決めたら機械に数えさせる」ことにしている。 下の 3 本は .github/workflows/ci.yml の fast ジョブで落ちると止まる。

スクリプト何を見るか踏んだ事故
scripts/check_forbidden_patterns.py 一度「やらない」と決めた書き方が残っていないか。現行の規則:
  • .fetchOffset = を使わない（キーセット・ページングにする）
  • ObservableObject / import Combine を使わない
  • isStoredInMemoryOnly: true は MosaicSupport.makeInMemoryModelContainer だけ
  • キーセットの述語（$0.X > cursor）を持つファイルでは、その列の SortDescriptor に comparator: .lexical が要る
  • 人を指す文字列（refKey / faceID / coverFaceID / name）を持つ台帳モデルは、 書き出しの匿名化に載っていること
 ADR-143 が「オフセットで送らない」と決めたのに DropboxCacheStore だけ残り、 実機で 1 回 35 秒＋行の取りこぼし（ADR-239）。並列テストの ModelContainer 競合で テストの実行体だけが消える（ADR-245）。新テーブルが匿名化から漏れ、 書き出した台帳に実フォルダ名が残る状態（ADR-243 の副産物）
scripts/check_diagnostic_strings.py 実機確認の手順（device-verification.md の <!-- expected-diagnostics -->）が指している診断ログの文字列が、 コードに実在するか。⚠️ コメント行は数えない 手順は「driver: turn= で交互になっている」と書いてあるのに、実装整理で その行を消していた——実機で 1 晩かけても何も確かめられない＝手順が静かに死んでいた。 ⚠️ しかも最初の版は grep -rlF だったので「この行を消すな」という説明コメントが当たってしまい、 本体を消しても通っていた（ADR-248 と同じ回で発見）
scripts/check_removed_symbols.py 公開シンボルを消したときに、参照が残っていないか（差分ベース） —
⚠️ 足すときの決まり

新しい規則を決めたら呼び出し側に if を足すのではなく、ここに行を 1 つ足す。 それが「11 の述語に増えた」経緯そのものだった（ADR-196）。

⚠️ 検査を書いたら、それが捕まえるはずの退行を実際に起こして確かめる（負の検証）。 書いた直後は「捕まえるつもり」と「捕まえる」の区別が付かない—— 上の 2 本はどちらも書かれた理由そのものの退行を見逃していた。

⚠️ 規則は「モデルの数」ではなく「持っている列」で書く。 匿名化の検査を最初「台帳の全モデルが載っていること」と書いたら、 id が UUID で埋め込みしか持たない FaceCorrection で誤検知した。

⚠️ テストの規律（ADR-119/241/244/245/248）

詳細は テスト戦略 にあるが、規約として要点だけ。

  • 規模で壊れるコードは、規模のテストで止める（ADR-119）。 検証するのは時間ではなく回数。形は「規模を 4 倍にして、回数が比例して増えないこと」。
  • 時間ではなく出来事を待つ（ADR-241）。固定の Task.sleep は 「たぶん足りるだろう」という定数で、他のテストが増えるたびに黙って足りなくなる。 ⚠️ 定数を調整する対処を 2 回続けたら、待ち方そのものを疑う。
  • 繰り返し走る処理は「2 回目」をテストする（ADR-244）。 ⚠️ 無限ループは繰り返しの性質なので、1 回のテストからは原理的に見えない。 同時に「まだ諦めない」側も固定する（片方だけだと逆の不具合になる）。
  • テストの中で「1 つ選ぶ」をしない（ADR-248）。 first / randomElement / 辞書やセットの走査順はテストを確率的にする。 候補が複数なら全部見る。
  • ⚠️ fixture の前提を assert する。「空でも通る assert」を書かない。 fixture に入っていないものは、どんな検査も見つけない。

検証ポリシー

  • 個人写真が入った環境のアプリ画面スクショは撮らない（個人写真が写り得る）。日常の検証はビルド・ログ・ユニットテスト・コンテナ内ファイル件数で行う。
    ただし資料・ヘルプ用のスクリーンショットには回避策が確立している（ADR-114）——使い捨ての専用シミュレータ「MosaicShots」を simctl create で作り、フリーライセンス素材（Lorem Picsum・Unsplash License）だけを addmedia し、EXIF 注入（GPS・撮影日）で旅行/場所/日付グリッドまで実データで埋めて撮る。個人写真が 1 枚も入らないので禁止事項に抵触しない。スクリプトは scripts/{fetch_screenshot_photos.sh, inject_screenshot_exif.swift, make_screenshot_sim.sh, export_screenshots.py}＋MosaicPhotosUITests/ScreenshotCaptureTests。落とし穴: simctl privacy grant photos は iOS 26 で効かない（UITest でダイアログをタップして許可する）／xcodebuild test の既定のデバイスクローンでは写真も権限も無いので -parallel-testing-enabled NO が必須。
  • 破壊的操作（消去・初期化・上書き）はユーザー環境に対して事前確認。検証は使い捨て環境で。
  • git push は明示指示があるときだけ。作業は基本 main 上で行いブランチは作らない。
