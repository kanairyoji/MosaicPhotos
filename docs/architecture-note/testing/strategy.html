テスト戦略の全体像

テストは 3 層で考える：(1) 純ロジックの単体テスト（macOS で秒速・大多数）、(2) OS 依存の統合テスト（iOS シミュレータ）、(3) データセット評価（検出性能を数値で判定・次ページ）。この 3 層が成立するのは、アーキテクチャ側で「ロジックを純関数と seam に寄せる」設計を貫いているからで、テスト戦略とパッケージ構成は表裏一体である。

2 系統の実行環境（scripts/test.sh）

系統対象実行速度
FASTFoundation のみの純ロジック（AutoAlbumCore / FaceCore / PeopleKit / PhotoSourceKit / MosaicSupport / BackupKit / DropboxKit / LocalPhotoCore / ImageCacheKit / PerceptionCore）macOS の swift test各パッケージ数秒〜十数秒
IOSUIKit / SwiftData / Photos に依存するもの（DropboxCore / PhotosFeatureKit）と UI テストiOS シミュレータの xcodebuild test分オーダー

scripts/test.sh all が両系統を一括で回す。各 SPM パッケージは .iOS(.v17) 宣言＋@available ゲートで macOS でもビルド可能に保っており、これが FAST 系統の前提になっている（アプリ本体の最小 iOS は 26.0）。

テストを可能にしている設計

  • 純ロジックへの分離 — 検索の融合（AIAlbumSearcher）・語彙接地（VocabularyGrounding）・顔クラスタリング（FaceClustering）・日付解釈（RelativeDateParser）などは Foundation だけで動く純関数/値型。モデルも DB もネットワークも無しでテストできる。
  • seam（プロトコル注入） — 外部依存はプロトコルで抽象化しデフォルト引数で本番実装を注入する。HTTPClient（URLSession）/ DateProvider / AccessTokenProvider / 知覚系（TextEmbedder / ConceptExpander / FacePerceptionProvider…）。テストはスタブを渡す。CLIP の「近さ」も seam なので、接地の規則は固定ベクトルで完全にテストできる。
  • @ModelActor はインメモリで — SwiftData のストア（TagStore / FaceStore 等）はインメモリで生成してストア連携までテストする。 ⚠️ 生成は MosaicSupport.makeInMemoryModelContainer(for:) だけが行う（ADR-245）。 isStoredInMemoryOnly: true の直書きは禁止で、scripts/check_forbidden_patterns.py が CI で止める。 理由は下記「⚠️ テストが落ちているのに『重い』に見える」。

⚠️ プロセス全体で 1 つの状態を触るテスト

swift-testing の Suite は既定で並列に走る。.serialized はその Suite の中だけを直列にするので、別々の Suite が同じ「プロセス全体で 1 つの状態」を書き換えると壊れる。しかも単体では再現せず、実行のたびに落ちる本数が変わる——同じ形で 2 回踏んだ。

踏んだ状態症状対処
BackgroundYield.environmentOverrideForTesting隣の Suite が .active を差している間、再評価が「前面だから降りる」で 1 件も進まないこの上書きを使うテストを 1 つの .serialized Suite へ集めた
UserDefaults.standard（オフロードの停止記録・設定）実行のたびに 2〜8 本が落ちる。CI で初めて赤になった（手元の全体実行はたまたま通っていた）同上。2 つの Suite を 1 つへ統合（片方を extension にする）

対処は 2 つのどちらか——(1) 使い捨ての状態を注入する（TestDefaults.scratch / PendingMetadataStore(directory:) のように seam を用意する）か、(2) 触るテストを 1 つの .serialized Suite に集める。(1) が取れるなら (1) が良い（並列のまま速い）。本番コードが .standard を直接読む場合は (2) になる。

⚠️ 非同期を「時間」で待たない（ADR-241）

背景処理のテストで Task.sleep(200ms) のような固定の待ちを置くと、込み合った回だけ何も起きないまま緑になる。単体では落ちるのに全体実行では通る——いちばん見つけにくい形の偽陽性で、ADR-119 の「空でも通る assert を書かない」が非同期の待ちでも出る。

やりたいこと× 時間で待つ○ 事実で待つ
仕込んだ失敗を踏ませるsleep(400ms) のあと結果を見るrequestLog にその往復が載るまで待つ
「同時に走っていない」を見る遅延の半分で覗く1 本目が始まり、かつ 2 本目が別の道（longpoll）へ回ったことまで待つ
処理が終わったことを見る件数がそろうまで待つ完了の印（initialSyncCompletedAt 等）が立つまで待つ。件数は途中でもそろう

⚠️ 観測点の選び方にも同じ罠がある。偽 Dropbox の callCounts() は応答を返した後に積むので、飛行中のリクエストが見えない——「同時に走っていないこと」を見たいのに、遅い応答ほど数えられなくなる（最初にこれで 0 件と出た）。入口で積む requestLog を使う。

⚠️ 仕込みの当たり先も確かめる。FakeDropboxServer のエンドポイント指定は部分一致なので、files/list_folder は list_folder/longpoll にも get_latest_cursor にも当たる。確かめたい経路の前提まで壊していないか見る。

⚠️ この罠は 3 回踏んだ（ADR-241）。1 回目は「待ちを延ばす」、2 回目は「上限を経過時間から 導く」と定数を調整する対処を 2 回続け、3 回目でようやく「時間で待たない」に到達した。 定数を調整する対処を 2 回続けたら、待ち方そのものを疑う。

  • 道具は waitUntil(timeout:_:)（短い刻みで条件を見る・上限は寛容に）。 ⚠️ 上限を切り詰めても検出力は上がらない——起きない不具合は上限まで待っても起きない。 短い上限は混んだ CI での誤検知を増やすだけ。
  • ⚠️ .serialized では足りない。Swift Testing が直列にするのはそのスイートの中だけで、 別のスイートは同じ実行で並行に走る。実際、別スイートに重い fixture を足しただけで 時間依存のテストが飢餓して落ちた。
  • ⚠️ fixture の規模は「何を確かめたいか」から決める。 キーセット・ページングの継ぎ目を確かめるのに本番のページ幅（5,000）を使っていたので 1 スイートで 1 万行の挿入になり、同じ実行の他のテストから CPU を奪っていた。 継ぎ目は規則の問題でページの大きさに依らないので 25 行で跨げばよい。

⚠️ 何度も呼ばれる seam は「最後の 1 回」で見ない

スタブが受け取った値を asked = refKeys のように上書きで覚えると、その seam が 1 回の操作で複数回呼ばれるとき最後の呼び出ししか見えない。途中の 1 回だけが間違っている状態を、まるごと見逃す。

実例: 共有の反映は 1 回の syncNow でも解析データの組み立てを「コピー前」「コピー後」の 2 度通り、さらに予約された反映が続くので3 回呼ばれていた。2 回目が間違っていても 3 回目が正しければ緑になり、規則を壊す変異が素通りした。Set に累積したら捕まった。

⚠️ 「何回呼ばれるか」を知らないまま最後の値を見るのは、たまたま最後が正しいことに賭けているのと同じ。累積するか、呼び出しごとの列を残す。

⚠️ 並べ替えを試すなら、入力の順番をわざとずらす

「近い順に並べてから上限で切る」を確かめるテストを、id 順＝近い順の入力で書いてしまうと、切ってから並べる誤りが素通りする——どちらの実装でも同じ答えが出るため。実際にそう書いて、変異（prefix を sort の前へ移す）を入れても緑のままだった。

順序に意味のある処理（並べ替え・打ち切り・優先度・先勝ち/後勝ち）を試すときは、生成順と期待順を必ず食い違わせる。上の例では「id が大きいほど近い」入力にして、期待値を [5, 4] にしたら捕まるようになった。

⚠️ これは ADR-119 の「空でも通る assert を書かない」と同じ形。テストが本当にその規則を守っているかは、規則を壊して確かめるのが唯一の確認方法で、緑であること自体は何も保証しない。

⚠️ 「待つ側」の上限もテストから縮める

譲り待ち・再試行・タイムアウトの上限が定数のままだと、その経路を通るテストがその秒数だけかかる。実際に「譲ったまま畳む」顔スキャンのテストが 1 本 61.6 秒かかっていた（既定の譲り待ち上限が 60 秒）。maxPauseNs を引数に出して 30ms を渡したら 0.33 秒になった。

判断の閾値（batchSize / betweenBatchNs / maxPauseNs）は既定値つきの引数にしておく。本番の呼び出しは変わらず、テストだけが現実的な速さになる。⚠️ 逆に、閾値を跨ぐことに意味があるテストでは縮めない（ADR-119 の「打ち切り上限を入れたなら、テストの規模はその上限を跨ぐこと」）。

⚠️ 繰り返し走る処理は「2 回目」をテストする（ADR-244）

背景で繰り返し走る処理のバグは、1 回の実行としては全部正しいことがある。 実機で「読めない写真 1 枚のために毎時 11 秒の列挙が永久に続く」を見逃したとき、 FaceTaggerRecordingTests は不変条件を 5 本で守り、 「何も解析できない provider」まで用意してあった。 ⚠️ それでも見逃した理由はどのテストも scan を 1 回しか回していなかったから。 「記録しない」は 1 回で確かめられるが、「次の窓でまた来るか」は 2 回目が無いと見えない。 無限ループは繰り返しの性質なので、1 回のテストからは原理的に見えない。

  • 見るのは回数（provider に訊いた回数・記録の行数）。 ADR-119 の「規模を 4 倍にして回数が比例しないこと」の姉妹形＝ 「窓を 2 回にして仕事が増えないこと」。
  • ⚠️ 同時に「まだ諦めない」側も固定する。片方だけ書くと、 一時的な失敗を永久に捨てる逆の不具合になる （譲り・回線断は 1 つの窓で何千枚も巻き込むため）。
  • ⚠️ 負のキャッシュを足したら忘れる経路のテストも対で書く（ADR-82）。
  • ⚠️ 費用も問う（ADR-247）。「2 回目は何もしない」が正しくても、 毎回払っている準備の費用は別の問い。実機では「やることが無い」と正しく 判断する前に 8.6 万行を 2 回読んでいた（+341MB）。判断を純 enum に出してテストする。

⚠️ テストが落ちているのに「重い」に見える（ADR-245）

並列のスイートが同時に ModelContainer を作ると、まれに CoreData の _generateTriggerSQL の中で SIGSEGV する。 ⚠️ 症状が分かりにくい——テストの実行体だけが消え、swift-test は 0% CPU で待ち続けるので「ハングした」ように見える。 ログは途中でぶつ切れ、失敗は 1 件も報告されない。

  • 対策は 2 つ必要: 名前を毎回変える（同名のインメモリ構成はプロセス内で同じストアを共有する） ＋生成を直列にする。両方を makeInMemoryModelContainer(for:) に閉じ込めた。
  • ⚠️ 見分け方: 「重いから遅い」と「落ちている」は プロセスの CPU と ~/Library/Logs/DiagnosticReports を見れば 1 分で分かる。 0% CPU で伸びないログは後者。これを 2 回「評価テストは長いから」と誤診した。
  • ⚠️ この症状は半年で 5 回観測され、unresolved-problems.md に 同じスタックトレースと同じ対策が 12 日前から書かれていたのに、読まずに再発見した。 症状で台帳を引く（grep -i "signal 11" docs/architecture-note/records/）。

⚠️ テストの中で「1 つ選ぶ」をしない（ADR-248）

文字列カタログの検査が、当たるキーを catalog.keys.first { … } で1 つだけ 選んでいた。Int の補間は実行時に %lld にも %d にもなり得るので カタログには両方が載っており、片方だけ訳があった。 Dictionary.keys の順序はプロセスごとに変わる（Hasher の種）ので、 同じコードで通る回と落ちる回になっていた。

  • ⚠️⚠️ 落ちた回が正しかった: 本番で引かれるのは未翻訳の側で、 人物一覧の枚数が実機で英語のまま出ていた。通った回を見て「問題なし」としていた。
  • 規則: 候補が複数なら全部見る（どれが実行時のキーになるかソースからは決まらない）。 first / randomElement / 辞書やセットの走査順はテストを確率的にする。 製品コードには「取得順は不定なので決定的に選ぶ」（ADR-94/139）と書いてあったが、 同じ規則がテスト側に無かった。
  • ⚠️ 「通る回と落ちる回がある」を flaky として流さない。 まず「どちらが正しいか」を決める。
  • ⚠️ fixture に入っていないものは、どんな検査も見つけない。 台帳の書き出しのバイト検査は「本名とフォルダ名が残らない」を見ているのに、 新しく足したモデルの行が fixture に無かったので漏れを見逃して通っていた。 fixture の前提を assert する。

実機ログも「テスト」の一部

シミュレータ・macOS では再現しない問題（ANE デッドロック・メモリ飢餓・OS スロットル・Core ML の fp16 破綻）があるため、実機の診断ログ（Diagnostics・PerfTrace・MetricKit）を継続的に読む運用を検証の最終段に置いている。「Mac で正常＝実機で正常」ではない、が繰り返し得られた教訓（詳細は診断と堅牢性）。

回帰の守り方

  • 実障害はテストで固定してから直す — 「バレエの太郎に無関係な写真が混ざる」→ HardGroundedContentTests、「まとめて確認で混ざった 2 人を分割できない」→ PersonCleanupTests のように、機序を再現する最小テストを残す。
  • 検出性能は回帰フロア — カテゴリ別 F1 の下限（現状値 −0.03）と全体 precision ≥ 0.97 をテストとして固定。フロアを意図的に割るトレードオフは台帳に理由を書いてから更新する。
  • CI — GitHub Actions が push ごとに scripts/test.sh fast をゲートに回す（iOS シミュレータはベストエフォート）。データセットが無い環境では評価系テストは安全にスキップされる。
