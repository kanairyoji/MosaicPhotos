テスト戦略の全体像

テストは 3 層で考える：(1) 純ロジックの単体テスト（macOS で秒速・大多数）、(2) OS 依存の統合テスト（iOS シミュレータ）、(3) データセット評価（検出性能を数値で判定・次ページ）。この 3 層が成立するのは、アーキテクチャ側で「ロジックを純関数と seam に寄せる」設計を貫いているからで、テスト戦略とパッケージ構成は表裏一体である。

2 系統の実行環境（scripts/test.sh）

系統対象実行速度
FASTFoundation のみの純ロジック（AutoAlbumCore / FaceCore / PeopleKit / PhotoSourceKit / MosaicSupport / BackupKit / DropboxKit / LocalPhotoCore / ImageCacheKit / PerceptionCore）macOS の swift test各パッケージ数秒〜十数秒
IOSUIKit / SwiftData / Photos に依存するもの（DropboxCore / PhotosFeatureKit）と UI テストiOS シミュレータの xcodebuild test分オーダー

scripts/test.sh all が両系統を一括で回す。各 SPM パッケージは .iOS(.v17) 宣言＋@available ゲートで macOS でもビルド可能に保っており、これが FAST 系統の前提になっている（アプリ本体の最小 iOS は 26.0）。

テストを可能にしている設計

  • 純ロジックへの分離 — 検索の融合（AIAlbumSearcher）・語彙接地（VocabularyGrounding）・顔クラスタリング（FaceClustering）・日付解釈（RelativeDateParser）などは Foundation だけで動く純関数/値型。モデルも DB もネットワークも無しでテストできる。
  • seam（プロトコル注入） — 外部依存はプロトコルで抽象化しデフォルト引数で本番実装を注入する。HTTPClient（URLSession）/ DateProvider / AccessTokenProvider / 知覚系（TextEmbedder / ConceptExpander / FacePerceptionProvider…）。テストはスタブを渡す。CLIP の「近さ」も seam なので、接地の規則は固定ベクトルで完全にテストできる。
  • @ModelActor はインメモリで — SwiftData のストア（TagStore / FaceStore 等）は isStoredInMemoryOnly: true で生成してストア連携までテストする。

⚠️ プロセス全体で 1 つの状態を触るテスト

swift-testing の Suite は既定で並列に走る。.serialized はその Suite の中だけを直列にするので、別々の Suite が同じ「プロセス全体で 1 つの状態」を書き換えると壊れる。しかも単体では再現せず、実行のたびに落ちる本数が変わる——同じ形で 2 回踏んだ。

踏んだ状態症状対処
BackgroundYield.environmentOverrideForTesting隣の Suite が .active を差している間、再評価が「前面だから降りる」で 1 件も進まないこの上書きを使うテストを 1 つの .serialized Suite へ集めた
UserDefaults.standard（オフロードの停止記録・設定）実行のたびに 2〜8 本が落ちる。CI で初めて赤になった（手元の全体実行はたまたま通っていた）同上。2 つの Suite を 1 つへ統合（片方を extension にする）

対処は 2 つのどちらか——(1) 使い捨ての状態を注入する（TestDefaults.scratch / PendingMetadataStore(directory:) のように seam を用意する）か、(2) 触るテストを 1 つの .serialized Suite に集める。(1) が取れるなら (1) が良い（並列のまま速い）。本番コードが .standard を直接読む場合は (2) になる。

実機ログも「テスト」の一部

シミュレータ・macOS では再現しない問題（ANE デッドロック・メモリ飢餓・OS スロットル・Core ML の fp16 破綻）があるため、実機の診断ログ（Diagnostics・PerfTrace・MetricKit）を継続的に読む運用を検証の最終段に置いている。「Mac で正常＝実機で正常」ではない、が繰り返し得られた教訓（詳細は診断と堅牢性）。

回帰の守り方

  • 実障害はテストで固定してから直す — 「バレエの太郎に無関係な写真が混ざる」→ HardGroundedContentTests、「まとめて確認で混ざった 2 人を分割できない」→ PersonCleanupTests のように、機序を再現する最小テストを残す。
  • 検出性能は回帰フロア — カテゴリ別 F1 の下限（現状値 −0.03）と全体 precision ≥ 0.97 をテストとして固定。フロアを意図的に割るトレードオフは台帳に理由を書いてから更新する。
  • CI — GitHub Actions が push ごとに scripts/test.sh fast をゲートに回す（iOS シミュレータはベストエフォート）。データセットが無い環境では評価系テストは安全にスキップされる。
