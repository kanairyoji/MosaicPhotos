Dropbox のテスト（偽サーバー）

Dropbox に関わる不具合は「1 回の応答」ではなく 反映を何度も繰り返したときの収束として現れる——重複コピーが 1,300 件生まれる、掃除が空回りする、消した写真が一覧に残る、同期が永久に止まる。こうした形は、決められた応答を順に返すスタブでは構造的に再現できない。そこで FakeDropboxServer は状態を持つ偽の Dropbox として作ってある。ネットワークは使わない。

作り

アプリの通信はすべて HTTPClient プロトコル越しに行う。本番は URLSessionHTTPClient、テストは偽サーバーを差す——差し替えはこの 1 点だけで、ソケットもローカルサーバーもポートも使わない。偽サーバーは URLRequest を受け取り、URL からエンドポイントを判定して (Data, HTTPURLResponse) を自分で組み立てて返す actor である。だから速い（BackupKit の 338 本が 14 秒）し、ポート衝突も順序依存も起きない。

ダミーを返すだけと違うのは、状態を持つ点にある。

持ちもの内容
filespath_lower → content_hash・サイズ・rev・表示名
bodiespath_lower → 実際のバイト列（download はこれを返す）
changeLog(通し番号, パス, 消えたか) — 差分同期（longpoll → continue）の材料
cursorsページ送りの続き（has_more → continue）

アップロードすれば files に入り、次の list_folder に現れ、download で同じバイト列が返る。content_hash は本物と同じアルゴリズム（DropboxContentHash）で計算するので、アプリの検証経路（アップロード直後の照合・オフロード直前の照合）がそのまま通る。これが「2 回反映したら収束するか」を試せる理由である。

異常の仕込み方（1 本のルール表）

「どのエンドポイントの・どのパスに・何回・何を起こすか」を 1 行で書く（ADR-204）。

let server = FakeDropboxServer()
await server.upload(path: "/a.jpg", data: bytes)          // 置く

await server.inject(.init(endpoint: "files/upload",       // 仕込む
                          pathContains: ".mosaic",
                          times: 2,                        // -1 = ずっと
                          effect: .status(429, retryAfter: 3)))
…
#expect(await server.pendingFaults().isEmpty)             // 仕込みが実際に使われたか
print(await server.transcript())                          // 落ちたとき何が起きたか
効果（Effect）作れる状況
.status(code, retryAfter:)429（レート制限・書き込み競合）/ 403（権限なし）/ 507（容量不足）/ 409（衝突・カーソル失効）など。Retry-After ヘッダも返せる
.truncateBodyHTTP 200 なのに中身が途中で切れている——hash 照合が存在する理由そのもの
.delay(milliseconds:)遅い応答（タイムアウト・並行数・待ち行列の挙動）
.networkError接続そのものの失敗
.drop応答を返さない。⚠️ キャンセルされるまで戻らないので、キャンセルの効かない呼び出しに使うと止まる

times が要点である。恒久的な失敗しか作れないと「失敗が続いたあと、直ったら収束するか」を確かめられない——オフロードは写真を消してから印を書くので、そこがいちばん大事な性質になる。

pendingFaults() で「使われなかった仕込み」を検査できる。 テストが緑でも、仕込んだ失敗が経路に当たっていなければ何も確かめていない。

観測（落ちたときに読むもの）

API用途
transcript()人が読める通信記録（POST files/upload /a.jpg → 200 (12 B ↑ / 48 B ↓)）
callCounts()エンドポイント別の回数。回数で見る規模テスト（ADR-119）にそのまま使える
dump()いまサーバーに在るものを 1 行ずつ（収束しないテストの原因調査）
trafficBytes()送受信の合計。「回数は同じだが量が増えた」を捕まえる

この偽サーバーで再現できること

  • 差分同期 — get_latest_cursor → longpoll → continue。サーバー側の増減が反映されるか、変化が無い回に書き直していないか
  • カーソル失効（reset）— ここから ADR-203 の欠陥（同期が永久に止まる）が出た
  • ページング — has_more を跨いで全件そろうか／途中で失敗した回に部分結果を渡していないか
  • 同名衝突 — mode=add の 409 → autorename で別名保存され、実際の保存先が返る
  • 非同期ジョブ — 即完了／N 回 in_progress の後で完了／クライアントにはタイムアウトだがサーバーでは完了（実障害の再現）
  • オフロードの印 — 書いて、読む側と同じ手順（カタログ → 載っているシャードだけ）で辿り直せるか
  • 容量不足・権限なし・時計のずれ・アカウント切り替え
⚠️ 弱い偽物は、経路をまるごと隠す

同じ日に 2 回踏んだ。get_metadata が size を常に 1 で返していたためオフロードの照合が必ず失敗し、その流れをどのテストも通っていなかった。files/upload が mode=add を無視して上書きしていたため同名衝突の経路が存在しなかった。どちらも「テストは緑だが、その経路を一度も通っていない」状態である。

だから 状態を持つ偽物は 1 つだけにしてある（以前は 5 つ併存していた）。忠実度の不足を直せば、その瞬間に全テストへ効く。新しい壊れ方が要るときは Effect に 1 行足す——失敗の種類ごとにプロパティを増やさない。偽物そのもののテスト（FakeDropboxServerTests）も置いてある。

例外は「1 往復の組み立て/解釈」を見るスタブ（応答の分類・応答の列・無応答）。あれらは状態を模倣していないので、統合の対象ではない。

実機の代わりにはならない

本物の権限・レート制限・他端末からの同時変更・Dropbox 側の仕様変更までは再現しない。とくにオフロードは写真を消す機能なので、最初の 1 枚は実機で確かめる運用にしている（records/device-verification.md の Z0 / Z4 / Z5）。この偽サーバーが閉じるのは「アプリの中で筋が通っているか」までである。
