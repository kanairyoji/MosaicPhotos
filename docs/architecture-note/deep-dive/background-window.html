バックグラウンド処理枠（いわゆる「夜間処理」）のパイプライン

アプリが背面（スクリーンロック・アプリ切替）にあり、電源ポリシーを満たすとき、OS が BGProcessingTask で数分の実行枠（処理枠）をくれる。その処理枠で何を・どの順に・どの資源で進めるか、処理枠の外に何を持ち出すか、そして何晩で終わるかを、図と実測で説明する。

用語: バックグラウンド処理枠（＝「夜間処理」の正体） アプリが背面にあるとき OS が BGProcessingTask でくれる数分の実行枠のこと。本章では「処理枠」と略す。 コード・ログでは nightly / bgtask と呼んでいるが、条件は「電源接続（既定ポリシー）＋アプリが背面（ロック・アプリ切替）」だけで時刻は見ていない。昼間でも、充電しながらロックしていれば同じ処理枠が開く（コード名は据え置き）。

1.1 OS はどう決めているか（ベンダー情報と外部解析の要点）

予約（submit）は「候補に載せる」だけで、実行の可否は OS のスケジューラ DAS（Duet Activity Scheduler・dasd）が決める。Apple 自身が「予約から起動までの遅れは何時間にもなり得る」と明記している（開発者向け文書「Starting and terminating tasks during development」）。

要因（WWDC20「Background execution demystified」の 7 要因）BGProcessingTask への効き方このアプリで確認すること
1. 電池残量が危険域電源接続中に走るので事実上無関係—
2. 低電力モード同上（ただし低電力モードは Background App Refresh 自体を止める）低電力モード OFF
3. アプリの使用頻度（端末内の予測エンジン）緩い: 「ここ数週間に前面で使った」程度で足りる普段使っていれば OK
4. App Switcher（強制終了）スワイプで終了したアプリは候補から外れる。次に自分で起動するまで枠は来ないロック前にスワイプで消さない
5. Background App Refresh の設定全 background モードに効く親スイッチ（既定 ON・アプリ別に OFF 可）設定 → 一般 → App のバックグラウンド更新 → MosaicPhotos が ON
6. エネルギー／通信の予算電源接続中はエネルギー予算を消費しない—
7. レート制限「毎日充電するなら毎日 1 回」程度が想定。分単位の連続実行は前提にない—

加えて BGProcessingTask 固有の条件: 端末がアイドル（画面ロック・操作なし）かつ電源接続中に走り、ユーザーが端末を使い始めた瞬間に期限切れになる。requiresExternalPower = false は「電源なしでも走ってよい」という許可にすぎず、DTS は「電源なしでは一度も走らないこともあり、それは許容範囲の挙動」と回答している。逆に、ケーブルを挿すことが評価のトリガになり、挿してから 1〜2 分で起動した報告がある。

実測（diagnostics-73・2026-09-05） ロック 2 分 18 秒・2 分 24 秒・29 秒の 3 回で bgtask: submitted は毎回出たが bgtask: begin は 0 回。数分のロックでは開かないのが普通で、8/30 のように背面遷移直後に開くこともある（OS 裁量）。同じ設計上の制約は Apple の写真アプリ自身（解析は充電中の夜間）にもある。

なぜ拒否されたかを見る方法: iPhone を Mac に接続し Console.app でプロセス dasd を絞り、heavywork で検索する。DAS は活動ごとに BatteryLevelPolicy / DeviceActivityPolicy / ThermalPolicy / ApplicationPolicy / BudgetPolicy などの重み付きスコアを記録し、FinalDecision: Can Proceed か Must Not Proceed（根拠つき）を出す。開発中は Xcode のデバッガから _simulateLaunchForTaskWithIdentifier: で即起動できる（Developer Options の「Run BG routine now」は同じルーチンを前面で回す代替）。

OS の裁量に頼らない選択肢: (a) ADR-165 の「この画面を開いている間、解析する」（前面のまま進める）。(b) iOS 26 の BGContinuedProcessingTask——ユーザーがボタンを押して始めた作業を、ロック後もシステムの進捗 UI つきで続けられる。Apple は「自動のメンテナンス・バックアップ・写真同期には使うな」と明言しているので、明示的な「今すぐ解析（ロックしても続ける）」ボタンの形でなら適合する。進捗の報告が必須で、遅いとシステムが続行を尋ねる。未採用（要判断）。

2. 処理枠の中で何が起きるか（1 処理枠の時系列）

runHeavyWork は「起こす → 判断する → 待つ」の 3 拍子。重い処理は起こすだけで完了を待たない（待つと処理枠を食い潰して次が始まらない＝Fix C）。

3. ゲート（誰が誰に譲るか）

処理枠の中では画面が無いので UI への譲りは要らない（ADR-179）。残るゲートは資源保護だけ。

ゲート見る側意味根拠

見送りやすい形で書くと: ユーザーが待っている処理 > 生成 > 解析（顔・タグ・埋め込み）、バックアップは横に並ぶ（資源が別）。「誰も待っていない処理のために、待っている処理を遅らせない」（ADR-122 の向き）。

4. 処理枠の外へ持ち出すもの（ADR-181・fire-and-forget）

処理枠の中で完結させる必要があるのは「済み」の判断ではなく「意図の記録」だけ、という発見が ADR-181 の中身。転送そのものは OS に任せ、応答で判断する。

5. 何晩で終わるか（WBS 的な見積り）

「1 処理枠で進む量 × 1 日の処理枠数」で残作業を割る。処理枠数は充電習慣に依存する（就寝中の充電で 1 晩に数回〜十数回。OS は処理枠の間隔を空ける）。

6. レビュー（2026-09-05）: 流れの正しさ・性能の妥当性・単純化

修正した

指摘何が起きるか対処
spool の取り残し（ADR-181 の初版）期限切れで「積んだが OS へ渡せなかった」ジョブが残ると、次の処理枠では「転送中」として対象外になり、新しく積むものが無い処理枠では誰も拾わず永久に残る渡す処理を「この実行で積んだ分があるとき」から無条件に変更（対象ゼロの早期 return 側にも置く）。テスト flushIsUnconditional
死んだ設定キー backupDeferralStreakADR-180 で見送りを廃止した後も毎処理枠 0 を書いていた。読み手が「まだ見送りがある」と誤解するキーと書き込みを削除。maxGenerateDeferrals の古いコメントも整理

妥当と判断した（据え置き）

  • 顔とタグ/埋め込みの同時起動: ANE ゲートで直列化されるので合計は変わらず、順番回し（ADR-86/93 の名残）を持たないぶん単純。
  • バックアップの並行: 資源が重ならない（ADR-180）。ADR-181 で処理枠内の仕事はディスクだけになり、より軽くなった。
  • 生成の見送り上限 4: 5 処理枠に 1 回 ~26 s を失うだけ。生成が飢えない最小の保険。
  • 10 秒ポーリングの待ちループ: 通知に作り替えるほどの利得が無い。
  • 処理枠の冒頭の HomeStores.shared(): 背面起動では避けられない固定費。温かければ 0.1 s。
