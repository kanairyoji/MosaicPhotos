並行・バックグラウンド処理の詳細

「UI を止めない」を最優先に、重い処理をアクタ/バックグラウンドへ逃がし、ユーザー操作とメモリ状態に応じて譲る。ここでは実際のパラメータと制御まで踏み込む。

アクタ分離の地図

区分実体役割
MainActor各ストア・エンジン（@Observable）UI 状態・公開 API
専用アクタAutoAlbumStore（@ModelActor）/ DropboxCacheStore（actor）/ PlaceNameResolver（actor）DB・キャッシュ・地名解決の直列化
detachedTask.detached(priority: .utility)全件列挙・グリッド集約・署名計算など CPU 仕事
backgroundTask(priority: .background)CLIP 埋め込みの trickle 実行

原則: @Model はアクタ外へ出さない。境界をまたぐ値は Sendable（EnrichedPhoto / AutoAlbumInfo / PlaceCandidate）に変換する。

背景 CLIP 埋め込みパイプライン

全写真の画像埋め込みは PhotoTagger.embedUnprocessed が担う。一度に全部処理せず、小バッチ＋バッチ間スリープで trickle する。

func embedUnprocessed(

    betweenBatchNs: UInt64 = 2_500_000_000,   // 2.5s
    maxBatches: Int = 20_000,
    shouldPause: @MainActor () -> Bool = { false },
    onBatch: () async -> Void) async

未取得も sceneTagged=true] AP --> OB{16バッチ毎?} OB -->|はい| RA[onBatch → AI 再評価] OB -->|いいえ| SL RA --> SL[betweenBatchNs スリープ] SL --> CK

ポイント:

  • 未処理の抽出は limit 付き fetch（unembeddedRefKeys(limit:)）。全件ロードしない。
  • 取得不可でも sceneTagged=true にして無限ループを防ぐ（画像が無い/壊れた写真）。
  • onBatch は 16 バッチごとに呼び、AI アルバムを段階的に再評価（毎回やると重い）。
  • QoS は .background。UI 操作（.userInitiated）と CPU を奪い合わない。

「譲る」条件（協調的一時停止）

そもそも重い処理が動くのは BackgroundYield.heavyWorkAllowed（既定＝電源＋低電力OFF＋アプリ非アクティブ＋Wi-Fi。判定は4 軸の独立設定＝自動処理・控えめ・電源・回線）が真のときだけ。端末内写真だけを扱う処理は heavyWorkAllowedLocal（回線条件なし）を見る。加えて処理中も、次のいずれかが立つ間は 1 枚ごとに shouldPause を確認して 0.3s スリープで待機し即譲る（ADR-25。8 枚一括だと画面遷移が飢餓するため 1 枚単位）。

「譲れる処理」と「譲れない処理」を別ゲートにする（ADR-107） 上の 1 単位ごとの譲りが効くのはトリクル系（CLIP 埋め込み・顔スキャン・シーンタグ）だけ。AI アルバムの本番化（finalize）・ドリフト再評価・アルバム自動生成は一枚岩で、FM 解釈＋フル検索＋重心構築＋数万件の SwiftData が一続きに走り、始まるとユーザーが戻ってきても途中で譲れない。実機（diagnostics-46）では控えめ OFF の前面アイドルで finalize が起動し、以後の全操作が ANE ゲート待ち（実測 7.9s）・ModelActor 競合・CPU 競合で引っかかっていた。そこで BackgroundYield.monolithicHeavyWorkAllowed（＝heavyWorkAllowed ＋非アクティブ限定）を新設し、一枚岩だけをそちらへ移した。手動ブースト・デバッグ全開は明示操作なので免除。

また、譲り待ちは連続 60 秒で打ち切ってその実行を畳む（ADR-95）。眠ったまま「実行中」フラグを握り続けると、後から来た夜間 BGTask 窓が「すでに実行中」で弾かれて窓が丸ごと空転するため（実機で 14 分間フラグを握っていた）。各処理は差分ベースなので、畳んでも次の窓が続きから再開する。

  • ユーザー操作中 — グリッドのスクロール/スクラブ、画面遷移、写真ビュー表示中（タップ直後含む）。
  • メモリ圧迫中 — MemoryPressureMonitor.isUnderPressure（約 20 秒後に自動解除）。
  • クラウド取得中 — Dropbox サムネのドレイン中（cloudThumbnailBusy）・フル画像取得中（fullImageBusy）。

ANE 直列化ゲート（MLInferenceGate）

端末の Neural Engine は共有資源で、Vision の perform と Core ML の推論/ロードを同時に走らせるとデッドロックする（実機で確認。Vision が永久に返らず、顔スキャンが最初の 1 枚で固まった）。単体では固まらないので、直列化すれば回避できる。

論点採った設計理由
ゲートを掛ける場所ANE に触れる場所の内側（MobileCLIPRuntime / FaceModelRuntime / VisionTagAdapter / FacePerceptionAdapter）呼び出し側（夜間タガー）で包む方式は漏れる。実際、前景の検索経路が素通りしていた。また画像ロード（ANE を使わない I/O）までゲートに入り占有時間が伸びる
粒度段ごと（顔観測／クロップ再検証／埋め込みバッチ、概念埋め込みは 1 語ずつ）1 枚まるごと包むと顔の多い写真で数秒間ゲートを占有し、他の解析が飢える
優先度interactive / background の 2 列。解放時は interactive を先に起こす前景の検索が夜間バッチの待ち行列（タグ付けは同時 3 件が並ぶ）の後ろに回らないようにする
キャンセル待機中にキャンセルされたら自分の優先度クラスの先頭へ繰り上げacquire/release の 1:1 対応を壊さずに待ち時間だけ最短化する（待たずに抜けさせるとゲート未取得で本体が走る）
入れ子禁止。同一タスクの再入はタスクローカルで検出して素通し＋アサート非再入ゲートなので、入れ子で呼ぶと本当に固まる

残る最悪ケースとして、優先度は待機列の順序を変えるだけで実行中の保持者は横取りできない。モデルロード（CLIP 画像塔は実機 16〜35 秒）がゲート内で走るため、その最中に来た前景要求はロード完了まで待つ。ロードをゲート外へ出せば解消するが「ロードと推論の同時実行が ANE で安全か」は実機未検証のため、確認するまではゲート内に置いている。

計測はプロセス中断を跨がない

バックグラウンド実行中、OS はアプリを任意のタイミングで suspend する。ところが計測に使う時計は中断中も進み続けるため、実機ログに「メインスレッドが 29 分ブロックされた」「1 枚の画像ロードに 29 分」といった偽の値が並んでいた（実際は suspend と resume の間隔）。背景実行を診断するための仕組みが、背景実行でこそ壊れていたことになる。

対策として ProcessSuspension が 1 秒周期のタイマーで自分の発火間隔を見張り、大幅に遅れて発火したら中断とみなして世代を進める（メインスレッドの状態と独立に判定できるのが要点）。計測側は開始時の世代を控え、変わっていたらそのサンプルを捨てる。

Dropbox 側のスロットリング

  • サムネ並列数 — DropboxThumbnailBatcher がバッチで取得。並列数は設定（DropboxCacheSettingsKeys.thumbnailConcurrency）。
  • 初回同期の再代入間引き — ページごとに頻発する 8 万件規模（実機 86,172 枚）の再フェッチ/再代入を scheduleCacheRefresh でスロットル（先頭即時＋以降 ~0.4s 間引き）。

段階起動（スパイク回避）

起動直後に重い処理が同時に走らないよう時差で開始する（HomeLifecycleTasks）。詳細は 起動の高速化。

設計の勘所 「速く終わらせる」より「UI と端末を圧迫しない」を優先。trickle・QoS・協調的一時停止・段階起動の 4 つで、重い AI 処理を体感ゼロに近づけている。
