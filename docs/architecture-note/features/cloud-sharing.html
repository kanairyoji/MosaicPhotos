クラウド共有

選んだ写真を、バックアップとは別の共有フォルダへ Dropbox サーバー内のコピーで投影し、家族や友人に見せる機能（ADR-112）。写真だけでなくオンデバイス AI の解析結果（タグ・CLIP 埋め込み・顔）も同梱するため、受け取った側の端末は同じ写真を解析し直さない。

設計の中心：共有はバックアップの「射影」

この機能の出発点は「全部バックアップしたいが、家族に見せたいのは一部だけ」という要求だった。素直に考えると 3 つの案がある。

案容量不採用の理由
共有分を共有フォルダへ移動（実体 1 つ）増えない共有フォルダの中身がバックアップの一部になる。家族の誰かが消せばバックアップが欠ける——「バックアップは append-only の正本」という保証が失われる
共有リンク（URL）増えない散在する写真の集合に 1 本のリンクは張れない。相手の閲覧体験がリンク集になる
外部の無制限サービス（Amazon Photos 等）増えない公開 API が無い。無制限を掲げるサービスはほぼ例外なく自社アプリに閉じており、自動連携できない

採用したのはサーバーサイドコピーによる射影。共有分の容量が二重に計上される代わりに、正本（バックアップ・原本）には一切触れない。共有側で何が起きても——家族が消しても、フォルダを整理しても——バックアップは無傷で、共有側は次回の反映で自己修復する。

なぜコピーが軽いのか files/copy_batch_v2 は Dropbox サーバー内でファイルを複製するため、端末は「この 100 枚をあそこへコピーして」という 1 リクエストを送るだけで済む。写真データの再アップロードは発生しない。従量回線でも実用的に動く理由がここにある。

3 つの独立した機能

「受け取る」「提供する」「バックアップ」は別々に設定できる独立機能で、依存は一方向にひとつだけある。

機能必要なもの備考
共有を受け取るDropbox 接続のみバックアップも、自分の写真の提供も不要
クラウド写真を提供するDropbox 接続のみ原本が既に Dropbox にあるため直接コピーできる
端末写真を提供するバックアップ共有はバックアップ実体からのコピーなので、未バックアップの写真は「バックアップ待ち」になる

この依存関係は設計上避けられないが、体験としては隠す。共有セットに入っている未バックアップ写真は、次回バックアップの先頭へ並べ替えられる（BackupRunner の優先 ID）。数万枚の順番待ちの最後尾に置かれて何日も反映されない、という事態を防ぐためである。

レイアウト

/MosaicPhotos/<端末>/               ← 端末ごとのルート（ADR-175）
  Backup/                          ← バックアップ（全量・非共有・正本）
    2024/2024-03/IMG_0001.jpg …    ← 撮影年月で整理（ADR-176）
    .mosaic/                       ← 台帳（catalog＋撮影月シャード）
  Share/                           ← 共有ルート（ユーザーが Dropbox 側で家族に共有）
    People-<名前>/                  ← 共有セット＝サブフォルダ（種類の接頭辞つき）
      IMG_0123.jpg …
      .mosaic-share/shard-ab.json  ← 解析データ（content_hash 先頭 2 桁ごと・ADR-183）
      .mosaic-share/shard-cd.json

解析データは 1 セット 1 ファイルではなくシャード（shard-<xx>.json）。写真ごとの解析結果は不変なので、写真が増減しても触れたシャードだけが動く（12,941 枚のセットで 1 枚の増減＝25MB の作り直しだったものが 1 シャード・数十〜数百 KB）。旧 analysis-v1.json は受信側が読み続け、送信側はシャードを置いたら消す。

セットがフォルダとして見えるので、相手が MosaicPhotos を使っていなくても Dropbox 公式アプリでそのまま閲覧できる。使っている場合は、共有フォルダを同期ルートに追加するだけで（既存の複数ルート機構）ホームにアルバムとして現れる。

共有フォルダに置かないもの バックアップの台帳（全写真のメタデータ・位置情報を含む）は共有フォルダへ置かない。置くのは写真そのものと、その写真の解析結果だけ。共有していない写真の情報が漏れる経路を作らない。

解析データ（旧称サイドカー）：refKey ではなく content_hash で結ぶ

受け取った側で再解析させないために、解析結果を JSON で同梱する。ここで問題になるのが「同じ写真」をどう指すかである。

アプリ内の写真キー refKey（"L-<localIdentifier>" / "C-<Dropbox パス>"）は送信者と受信者で必ず違う。送信者の端末内 ID は相手の端末では無意味だし、パスも共有フォルダ側では変わる。そこで結合キーには Dropbox の content_hash を使う。

セクション内容版
tagsVision シーンタグ・OCR テキスト・人数・美的スコアタグ版
clipCLIP 画像埋め込み（Float16 512 次元・base64・約 1KB）知覚版（モデル ID 込み）
faces顔ごとの bbox・埋め込み・品質・撮影日顔スキャン版

人物名は設定で載せる／載せないを選べる（既定は載せる・ADR-167）。受け取った側は名前を「提案」として扱い、自分が既に付けた名前は上書きしない。

content_hash が効く理由 受信側の同期エンジンは list_folder の応答に content_hash を含めて受け取っている。追加のダウンロードなしで手元の写真と解析データのエントリを突合できる。パスにも refKey にも依存しないので、フォルダ整理や同名衝突の改名にも影響されない。

受信側の取り込み

取り込みは「版が一致するセクションだけ・既存レコードのある写真はスキップ」という保守的な規則で行う。受信側の自前解析が常に優先で、解析データは穴を埋めるだけである。

  • タグ・CLIP: 台帳へ登録し、夜間タガーはその写真を「処理済み」として推論をスキップする（adoptImportedEmbeddings）。クラウド写真の解析で最も重いのはサムネイルのダウンロードなので、通信・電池・時間がまるごと節約される。
  • 顔: 既存の逐次クラスタリングへ流し込む。同じ顔モデルの埋め込みなので、受信側で命名済みの人物へ自然に合流する——「共有された子供の写真が、自分の端末で名前を付けた人物のアルバムに自動で入る」という体験になる。
解析データは外部入力である 別のデバイスが書いた JSON をそのまま信じない。ファイルサイズ・エントリ数・タグ長・ベクトルの次元と有限性（NaN/Inf を弾く）を検査し、壊れたエントリは黙って捨てて自前解析に任せる。クエリ解釈で LLM の出力を接地する QuerySpecSanitizer と同じ思想である。

冪等性：リモートの非同期ジョブは「タイムアウト＝失敗」ではない

実装当初、実機で共有フォルダに約 1,300 件の重複（IMG (1).jpg 形式）が生成され、1 時間にわたる高負荷を招いた（diagnostics-52）。3 つの因子の掛け算だった。

  1. コピー完了のポーリングが 60 秒でタイムアウトし「失敗」と記録。しかし Dropbox 側のジョブは走り続ける。
  2. 次の反映が失敗分を autorename つきで再コピー。前のジョブの成果と衝突しないので別名で増える。リトライのたびに倍々。
  3. 増えた自分のコピーが 1 秒ごとに差分通知を発火させ、そのたびに 7 万件の全件フェッチ（1.2 秒）が走って CPU を飽和させた。

対策は「リトライを冪等にする」ことに尽きる。

対策内容
autorename 全廃宛先名は計画（SharePlanning）が決定的に割り当てる。同名は " 2" の連番。衝突は失敗エントリとして返る
採用（adoption）宛先が既に実在し中身が一致するならコピーせず記録だけ更新。タイムアウト後に完了したジョブの成果を回収する
ポーリング上限60 秒 → 4 分
重複の掃除name (N).ext 形式で、どの記録にも属さず元名が実在するものだけ削除（安全側の条件）
自己同期の抑制差分通知に変更パスを載せ、表示除外パス配下だけの変更なら全件フェッチをスキップ
一般化できる教訓 リモートの非同期ジョブは、クライアントが待つのをやめても走り続ける。「タイムアウト＝失敗」と決めつけたリトライは二重実行になる。冪等にする唯一の方法は実行前に実在を確認して採用することで、autorename のように「衝突を黙って回避する」機構はリトライと組み合わせると増殖装置になる。

反映の 1 回（ADR-183）

flowchart LR R[作成元へ追従
refreshAllFromSource] --> L[共有ルートを
list_folder(recursive) 1 回] L --> S1[解析データ（シャード）
差分同期] S1 --> C[copy_batch
500 枚/回・サーバー側] C --> D[delete_batch
外れた写真・墓標] D --> S2[今回コピーした分の
シャードを追記]
  • 一覧は 1 回: 共有ルートの再帰一覧（RemoteShareIndex）で全セットの写真の実在と解析データの content_hash を得る。以前はセットごとに create_folder＋list_folder＋実在確認（× 3 往復）。
  • 解析データは状態を持たない: 一覧にある各シャードの content_hash と、手元で組んだシャードの content_hash（同じ計算・決定的エンコード）を比べ、「無い／違う → 上げる、余る → 消す」（ShareAnalysisPlanning.plan）。消された解析データの復元（ADR-166）はこの規則に含まれる。
  • 解析データはコピーより先: コピーは 100 枚ごとのサーバー側ジョブ待ちで数分かかる。後回しだと「反映を押しても何分も更新されない」。
  • 作成元に自動追従: 人物・グループ・AI アルバムが育ったら共有セットも増減する。追従の解決では、端末に原本があるバックアップコピーと自分の共有ルート配下は載せない（解析候補と同じ規則）。

自己修復

  • 外部削除（家族が消した・整理した）→ 再コピー。解析データも同じ規則で復元。
  • 元写真の更新（編集して content_hash が変わった）→ 再コピー。
  • 一覧が取れない（通信断）→ その回は全部スキップする。実在不明のまま再コピーすると重複を作るため。

実行は「起動から少し遅らせて」「バックアップ完走後」「処理枠（充電中・ロック中）」「ハブの『今すぐ反映』」。自動実行は回線ポリシーに従う（バックグラウンドと省電力の依存ゲート表を参照）。受信側も家族フォルダごとに再帰一覧 1 回で全シャードの rev を得て、変わったものだけ落とす。

写真の本体には触れず、解析の輸出入は AutoAlbumEngine+Share / PeopleEngine+Share / FaceStore+ShareExport の薄い層が担う。アプリ（Composition Root）の ShareAnalysisAdapter が両者を橋渡しする——BackupKit が AutoAlbumCore / FaceCore に依存しないための seam である。
