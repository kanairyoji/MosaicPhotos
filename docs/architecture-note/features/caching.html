キャッシュ戦略

画像キャッシュのプリミティブ（メモリ + ディスク I/O）を ImageCacheKit に共通化し、端末写真と Dropbox の双方が利用する。破棄ポリシー（LRU）は利用側が持つ。

ディスクの上限は 1 つ（ADR-185） キャッシュごとの上限は持たない。予算＝端末の総容量の 10%（設定で 5% / 10% / 20% / 30% / 40% か固定 GB＝2〜100GB）を端末サムネ・Dropbox サムネ・Dropbox 本体画像・顔アバターが共有し、超えたら本体画像（先読み → 閲覧済み）→ 顔アバター → サムネ（端末・Dropbox を区別せず古い順）の順に捨てる。各層に床、空き 2GB の安全弁。実体は ImageCacheKit の CacheBudget / CacheBudgetPlanner（純ロジック）/ CacheBudgetCoordinator（actor）。各キャッシュは BudgetedCache で参加し、書き込み後に noteGrowth() を呼ぶだけ（判定はまとめて）。枚数もユーザーも見ない規則なので、ライブラリが育っても設定を変える必要がない。

2 層キャッシュ

NSCache} MEM -->|hit| RET[即返す] MEM -->|miss| DISK{DiskImageStore} DISK -->|hit| LOAD[読み込み→メモリへ→返す] DISK -->|miss| FETCH[ソースから取得→両層へ保存]
  • MemoryImageCache — NSCache ラッパー（メモリ層）。
  • DiskImageStore — ディレクトリ単位のディスク I/O と LRU 列挙。コアは Foundation のみ（macOS テスト可）、UIImage 便宜は #if canImport(UIKit)。

予算の参加者と、それぞれの「捨て方」

「いくら捨てるか」は協調役が決め、「どれを捨てるか」は各キャッシュが自分の LRU で決める（BudgetedCache）。

参加者層メタ管理古い順の決め方
LocalPhotoCore の ThumbnailCache（actor）サムネ—ファイルの mtime
DropboxCore の DropboxCacheStore（actor・サムネ／本体画像の 2 参加者）サムネ／本体画像SwiftData（CachedDropboxItem / CacheUsageEntry）CacheUsageEntry の最終アクセス（本体画像は先読み → 閲覧済みの順）
PeopleKit の顔アバター派生物—ファイルの mtime

Dropbox キャッシュの無効化

ファイルの contentHash 変更を検知してエントリを無効化する。バイナリは Caches/DropboxKit/{thumbnails,fullimages}/ にハッシュ化ファイル名（DropboxCacheNaming）で保存。

ユーザーが決めるのは「予算」だけ

設定（Storage 画面）で決めるのは全体の上限 1 つ（割合か固定 GB・キーは CacheBudget.Keys）。同じ画面に参加者ごとの使用量と合計を出す。種別ごとの上限キー（CacheSettingsKeys.diskLimitMB / DropboxCacheSettingsKeys の各 limit）は ADR-185 以降使っていない（メモリ層の上限＝memoryLimitMB は「Auto＝端末 RAM から算出」を既定に残る）。

設計判断 メモリ層と I/O プリミティブを 1 つのパッケージに集約しつつ、破棄ポリシーは各利用側が持つ。端末写真と Dropbox では無効化条件（contentHash の有無）も容量管理（SwiftData の有無）も異なるため、共通化しすぎず「プリミティブ共通・ポリシー個別」に留めている。
