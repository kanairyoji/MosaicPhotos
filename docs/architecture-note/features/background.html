バックグラウンドと省電力・通信制御

シーンタグ付け・CLIP 埋め込み・顔スキャン・自動アルバム生成といった重い処理は、原則としてアプリを使っていない時間帯（画面ロック中の BGProcessingTask）にだけ動かし、フォアグラウンドでは一切走らせない（ADR-25）。実行条件はユーザーが4 つの独立した軸で決める（ADR-80）。状況は最上部のアクティビティバーで可視化する。どの設定で何が動くかの正本は records/background-behavior.md。

なぜ「使っていない時だけ」なのか（ADR-25） 旧ゲートは「電源＋低電力OFF＋アイドル 60 秒」だった。充電しながら閲覧中に 60 秒触らないと重い処理が走り出し、操作を再開してもクラウド写真のタグ付け（1 バッチ最大約 27 秒）が譲れず操作が固まった。そこでアイドル判定を廃止し、「電源＋低電力OFF＋アプリ非アクティブ（scenePhase）＋Wi-Fi」に変更。フォアグラウンドでは重い処理をゼロにした。停止判定も全処理1 枚単位に統一し、操作・遷移が来たら即譲る。
「夜間処理」の実体 コード・ログで nightly / bgtask と呼ぶものは、充電中にアプリが背面にあるとき OS がくれるバックグラウンド処理枠（BGProcessingTask・数分）であり、時刻は見ていない。いつ開くかは OS の裁量で、ロックしてすぐには開かない。処理枠の中の時系列・資源・見積り・OS が枠をくれる条件は 専用の章にまとめた。待たずに進めたい場合は「今すぐ解析」（ADR-182）。

重い処理の実行条件（3 軸の独立設定 / ADR-80 → ADR-195）

当初は 5 段階の梯子（HeavyWorkTiming: paused / nightly / chargeActive / battery / unlimited）だったが、3 つの異なる軸を 1 本に混ぜていたため「電源接続は必須のままモバイル回線だけ許す」が表現できず、電源・回線が既存の PowerStateMonitor / NetworkStateMonitor の設定と二重になっていた（どちらか厳しい方が効く＝片方を緩めても動かない）。そこで梯子を解体し、独立した設定にした（当初 4 つ。「画像分析を控えめに動かす」の軸は ADR-195 で廃止し、いまは 3 つ）。すべての条件を満たしたときだけ重い処理が動く。

#軸設定場所選択肢既定
1自動処理設定 → アルバム → 処理のタイミング自動で解析する（オン / オフ）オン
2電源設定 → バックグラウンドとバッテリー充電中のみ / 常に / オフ充電中のみ
3回線同上Wi-Fi のみ / セルラーも / Wi-Fi かつ低データ以外 / オフWi-Fi のみ

軸 1（HeavyWorkTiming）は paused / enabled の 2 値だけを持ち、判定の純関数 allows(...) は電源・回線の状態を自分では持たない——呼び出し側の BackgroundYield が各モニタの backgroundAllowed() / networkAllowed() の結果を渡す。これで判定が一意になり二重設定が消える。旧 5 段階の保存値は起動時 1 回だけ migrationPlan（純関数・テスト済み）で各軸へ写す。

前面（アプリを使っている間）の扱いは設定ではなく常時の挙動（ADR-195）: 触っている間は動かさず、20 秒触っていなければ動き、触れば 1 単位で譲る。前面で起こすのは AnalysisDriver——起動・前面復帰・20 秒アイドル（120 秒ごとの再評価＝熱の回復や写真の追加もここで拾う）・電源・回線・ブースト終了の契機で方針を見て、許されていれば既存のトリクルを起こす。トリクルは 60 秒開かなければ畳み（ADR-95）、次の契機で駆動役がまた起こす。「再開」という状態は持たない——残作業そのものが状態。以前は前面で解析を起こす場所が無く（起動時 1 回＋電源/回線の復帰だけ）、その穴を「今すぐ解析」の自動再開で埋めた結果 5 軸の状態機械ができて 9 周壊れ続けた（case-studies）。

アプリ操作中✗ 動かさない（1 単位で譲る）✗

一枚岩の処理は「非アクティブ限定」に分ける（ADR-107） トリクル系（CLIP 埋め込み・顔スキャン・シーンタグ）は 1 単位ごとに heavyShouldPause() で譲れるので、前面アイドルでも安全。しかし AI アルバムの本番化（finalize）・ドリフト再評価・アルバム自動生成は一枚岩（FM 解釈＋フル検索＋重心構築＋数万件の SwiftData）で、いったん始まると数十秒〜数十分 ANE・CPU・ModelActor を占有しユーザーが戻ってきても途中で譲れない——これが「AI アルバムを触るといちいち固まる」の正体だった（diagnostics-46）。そこで BackgroundYield.monolithicHeavyWorkAllowed を新設し、heavyWorkAllowed に加えて非アクティブ（画面ロック・アプリ切替）限定にした。手動ブースト（「今すぐ処理」）とデバッグ全開は明示操作なので従来どおり前面でも動く。トレードオフ: 前面アイドルでも本番化は夜間 BGTask まで遅れることがある（プレビューは即時のまま）。

中央ゲートは 1 つの表（ADR-196）。BackgroundYield.verdict(for:) に「どの仕事か」（通信が要るか × 始めたら譲れるか ＋ 処理枠）を渡すと、止めている条件（Blocker）が「直しやすい順」に返る。免除は Exemption（平常 / 「今すぐ解析」 / デバッグ全開）の 1 軸で、条件ごとに「どの段なら素通りできるか」が表に書いてある。呼び手は部分集合を選べないので、入口の判定と 1 単位ごとの譲り判定が必ず一致する。

なぜ 1 つにしたか（11 述語が壊れ続けた） 以前は heavyWorkAllowed / heavyWorkAllowedLocal / monolithicHeavyWorkAllowed / heavyShouldPause / analysisShouldYieldToUI / uiBusy … と 11 の述語が条件の部分集合を持ち、どれを使うかが呼び手の知識だった。結果 (1) 入口（PeopleEngine.startScan＝heavyWorkAllowedLocal）が譲り（heavyShouldPause）より緩く、「入ってよい」と言われて 75,000 行を読んでから譲り待ちに入り 60 秒で 0 枚のまま畳む（diagnostics-62/63）、(2) 画面の「なぜ進まないか」が別実装で、ゲートが閉じているのに「すべての条件を満たしています」と言えた、(3)「控えめ」の軸を外した（ADR-195）ときに refinePlaceNames → generate が前面から到達可能になり ADR-107 の一枚岩ゲートをすり抜けた。述語は死にコードを 1 つ含み、debugForceHeavyWork の説明は実装と矛盾していた。

「誰が聞いているか」を表すグローバル状態も 4 つ（isAppActive / isAppInBackground / sessionActive / debugForceHeavyWork）から 2 つ（scenePhase / exemption）へ減らし、一時変更は withScenePhase / withExemption のスコープで入る。以前は処理枠が isAppActive を false に書き換えてゲートを開け、restoreAppActive という引数で後始末していた（戻し忘れがレビューで指摘されている）。設定 UI は Albums の Auto Albums 側「処理のタイミング」（軸 1）と General → Background & Battery（軸 2・3）に分かれる。

設定で外せない安全弁 どの設定でも、低電力モード・メモリ圧迫・写真ビュー表示中・フル画像/クラウドサムネ取得中・アルバム生成中・フォアグラウンド復帰直後 20 秒の間は重い処理を動かさない。また譲り待ちには上限があり、連続 60 秒開かなければその実行を畳む（ADR-95。眠ったまま「実行中」フラグを握ると夜間 BGTask 窓が丸ごと空転するため。各処理は差分ベースなので次の窓が続きから再開する）。

AI アルバム作成は 2 段階（即時プレビュー→その場で本番化）

UI を固めないため、AI アルバムの作成は 2 段階に分ける。作成時は決定的プレビュー（レキシコン＋日付＋タグ照合・LLM なし・1〜2 秒）で即座にメンバーを見せ、続けてその場で本番化する（finalizeNow・ADR-110＝FM 解釈＋フル評価＋証拠ゲート＋LLM 審査を十数秒。ユーザーの明示操作なので夜間ゲートの対象外・utility 優先度）。夜間に残るのは語彙接地（重心）がコールドのときの仕上げだけで、そのときは pendingFinalization が残り finalizePending が接地込みで仕上げる。「バレエ」のようなレキシコン外の語が翌朝まで条件にならなかった問題（diagnostics-49）はこれで解消した。

電源ゲート（PowerStateMonitor）

UIDevice.batteryState と ProcessInfo.isLowPowerModeEnabled を監視し、ポリシー BackgroundPowerPolicy（While charging=既定 / Always / Off）と合わせて backgroundAllowed() を返す。While charging は「電源接続（charging/full）かつ 低電力モード OFF」。

シミュレータ注意 シミュレータは充電状態を .unknown で返すため、charging/full のみで判定すると背景処理が全部止まる。「.unplugged と確定したとき以外は電源扱い」にしてロックを避ける。

回線ゲート（NetworkStateMonitor）

NWPathMonitor で isOnWiFi（Wi-Fi/有線）・isExpensive（従量）・isConstrained（低データモード）を監視し、ポリシー BackgroundDataPolicy（Cellular allowed / Wi-Fi only=既定 / Wi-Fi skip Low Data / Off）と合わせて networkAllowed() を返す。通信を伴う背景処理は backgroundAllowed() かつ networkAllowed() で実行する。

CLIP 埋め込みのスマート方針

埋め込みは回線NG時にクラウド写真（サムネDL）をスキップしてローカル写真だけ続行する（unembeddedRefKeys(limit:localOnly:) で DB 側に "L-" 前缀で絞り込み）。ローカルが尽きたら終了し、Wi-Fi/電源の復帰（onChange）で scheduleBackgroundFill() を再起動してクラウド分を拾い直す。

設定

アプリ横断の設定なので、機能別ではなく設定ルートの General → Background & Battery（BackgroundSettingsView）に「Power」「Background Data」を並べて置く。背景 CLIP の速度段階は Albums の Auto Albums 側（処理の重さ）に残す。
