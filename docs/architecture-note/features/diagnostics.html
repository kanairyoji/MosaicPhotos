診断と堅牢性

Mac/Console が使えない実機でも原因を追えるよう、端末上に診断ログを残す。SwiftData の起動時クラッシュは自己修復で回避する。

端末診断（Diagnostics）

アプリの init() で Diagnostics.install() を呼ぶと、次を Caches/diagnostics.log に記録する。

  • 未捕捉 ObjC 例外（NSSetUncaughtExceptionHandler）— 名前・理由・コールスタック。
  • メモリ圧迫（DispatchSource.makeMemoryPressureSource）— warning/critical とフットプリント。
  • LogChannel の各レベル — error は Release でも、info/verbose は DEBUG のみ転記。

Developer Options の DiagnosticsLogView で閲覧・共有・クリアできる。

注意 Swift の fatalError や SwiftData の trap はこのハンドラを通らず、標準クラッシュログ側に出る。

自己修復する ModelContainer

SwiftData の ModelContainer 初期化は、ストア破損やスキーマ不整合のとき起動時に trapし、実機で原因不明のクラッシュになりやすい。そこで resilientModelContainer(name:schema:policy:)（内部は makeResilientModelContainer）が段階的にフォールバックする。手を決める前に失敗の理由を見るのが要点で、容量不足やファイル保護（端末ロック中）のような一時的な失敗ではファイルを消さずその起動だけインメモリで動く。

容量不足・ファイル保護| M[ファイルは残しこの起動だけインメモリ] R -->|台帳（.ledger）| S{控えから戻せる?} S -->|はい| S2[StoreSnapshot から復元して再オープン] --> OK S -->|いいえ| C R -->|作り直せるキャッシュ| C[ストアファイル削除

データは失うが起動は止めない（失敗は診断ログへ）。AutoAlbumStore / TagStore / FaceStore / DropboxCacheStore / BackupEngine が採用する。

作り直せるキャッシュと台帳を区別する（ADR-186） 破棄していいのは再生成できるもの（付加情報・埋め込み・Dropbox キャッシュ＝.rebuildable）だけ。人物名やユーザー修正のように作り直せない台帳（FacesV1・BackupKit＝.ledger）は、アプリの版が変わった最初の起動で開く前に控えを取り（StoreSnapshot）、マイグレーションに失敗したら控えから戻して 1 回だけ開き直す。台帳側はスキーマの採番（破棄）ではなく optional 列の追加だけで進める。

⚠️ 台帳の健全さは、遷移に頼らず起動ごとに記録する（ADR-233/235/238）

「ユーザーの表明（名前・束ね・グループ所属）を失っていないこと」は、 遷移（再クラスタ・再スキャン・世代切り替え・掃除）の前後で数えて突き合わせる （AssertionCensus）。

  • ⚠️ 何も減っていなくても 1 行は出す——「出ていない」と「そもそも走っていない」を 区別できないログは、後から見て役に立たない。
  • ⚠️ 遷移は何週間も来ないことがある。解析が終わった端末では夜間の再クラスタの条件が 満たされず、実機ログでは 13.5 時間に 0 回だった。つまり「壊れたら勝手に分かる」は 「壊れる機会があったときに分かる」でしかなかった。 → reportLedgerHealth() を起動ごとに 1 回出す （faces: ledger clusters=… named=… groupMembers=N/M stale=K）。 ⚠️ 顔は読まない（全顔の走査は 4.5〜9 秒）。
  • ⚠️ 再スキャン中は言わない。持ち越しが進行中は「まだ戻っていない」だけで、 それを「失った」と呼ぶと毎晩誤報になる。

詳細は 台帳の守り方。 実機の台帳を控えて Mac で遷移を再演する仕組み（ADR-234）もそちらにある。

⚠️ テストが「ハング」に見えるクラッシュ（ADR-245）

診断の読み方として覚えておくべき形。並列のスイートが同時に ModelContainer を作ると、 まれに CoreData の _generateTriggerSQL の中で SIGSEGV する。

  • ⚠️ テストの実行体だけが消え、swift-test は 0% CPU で待ち続けるので ハングに見える。ログは途中でぶつ切れ、失敗は 1 件も報告されない。
  • 見分け方: プロセスの CPU と ~/Library/Logs/DiagnosticReports を見る。 0% CPU で伸びないログは「重い」ではなく「落ちている」。
  • ⚠️ この症状は半年で 5 回観測され、unresolved-problems.md に 同じスタックトレースと同じ対策が書かれていたのに、読まずに再発見した。 症状で台帳を引く（grep -i "signal 11" docs/architecture-note/records/）。

メモリ圧迫への対応

MosaicSupport.MemoryPressureMonitor が圧迫フラグを保持し、Diagnostics のメモリ圧迫ソースが warning/critical で立てる（一定時間後に自動解除）。背景の CLIP 埋め込みはこのフラグを見て一時停止し、jetsam を避ける。

CLIP の可視化

MobileCLIP.modelsBundled でモデル同梱の有無をロードせず判定でき、Developer Options に表示する。ランタイムのロード結果（成功/失敗/未同梱・所要時間・フットプリント）も診断ログへ残す。
