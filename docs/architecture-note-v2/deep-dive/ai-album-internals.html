AI アルバム実装詳細

自然文（任意言語）からアルバムを作る経路を、コードの登場人物と処理順で追う。設計の全体像はオンデバイス AIを先に。ここでは AIAlbumService を起点に「解釈 → 接地 → 検索 → 審査 → 増分評価」の各フェーズを実装レベルで説明する。すべて AutoAlbumCore（SwiftUI 非依存・macOS でテスト可能）にある。

まず例で追う

ライブラリ 86,000 枚・ピープルに「山田太郎」「山田花子」が命名済みという前提で、検索文「去年の沖縄で太郎が海で遊んでいる写真」からアルバムを作る流れを追う。

ステップ 1: 「作成」タップの瞬間（1〜2 秒・LLM なし）

まず LLM を使わない即時プレビューが走る。決定的な辞書とパーサだけで検索文を分解する：

検索文の断片解釈する部品結果
「去年」RelativeDateParser日付範囲 2025-01-01〜12-31（ハード条件）
「太郎」PersonNameGrounder顔クラスタ「山田太郎」に接地（ハード条件）
「海」JapaneseVisualLexicon（約 170 語）内容語 beach / sea / ocean（ランキング用）
「沖縄」（この時点では解釈されない）ステップ 2 の FM 解釈でカタログ接地され場所条件になる

検索は 3 段階で絞る：

  1. ハードフィルタ: 86,000 枚 →「去年」で 8,000 枚 →「山田太郎の顔がある」で 900 枚。足切りのみで順位は付けない。
  2. 3 本のランキング: 残り 900 枚を独立に順位付け。タグ＝シーンタグに beach 等を持つ写真（一致数順）／CLIP＝内容語のテキスト埋め込みと各写真の画像埋め込みのコサイン（上位バンドのみ採用）／字句＝地名・人物・OCR への文字一致。
  3. RRF 融合: 3 つの順位表を「順位の逆数の和」で 1 本に統合。複数の証拠がある写真が勝つ。単一スコアの閾値調整を捨てて「複数の目の合議」にしたのが要点。

ここまでで例えば 45 枚のアルバムがその場で表示される（pendingFinalization フラグ付き）。

ステップ 2: そのまま即時本番化（十数秒・ADR-110）

プレビュー表示の直後、同じバックグラウンドタスク（utility 優先度）がその場で本番化する（旧設計では夜間まで持ち越していたため、「バレエ」のようなレキシコン外の語が翌朝まで条件化されない実障害があった）。

  • FM 解釈（1 回だけ・永続化）: Foundation Models が検索文を構造化し、即時版で拾えなかったものを補う——「沖縄」を地名カタログに実在確認して場所のハード条件に、英訳を CLIP 用に、言い換えプローブを生成（採点は max-over-probes）。
  • 語彙接地: 内容語を実在タグへ展開する（VocabularyGrounding・タグ重心）。重心キャッシュがあるときだけ（groundingCachedOnly）——コールド構築（51k 埋め込み走査・実測約 2 分）を作成フローでは待たず、その場合は pendingFinalization を残して夜間が接地込みで仕上げる。全語がタグ語彙に完全一致（区切り正規化つき＝空白形と下線形を同一視）するなら重心不要で即接地。
  • LLM 審査: 候補ごとに「証拠行」を組み立てて keep / drop / unsure を判定させる：
#12 2025-08-14 | 沖縄県恩納村 | faces=2 | tags: beach, child, water   → keep
#31 2025-08-15 | 沖縄県那覇市 | faces=1 | tags: aquarium, fish, indoor → drop（水族館は「海で遊ぶ」ではない）

unsure は 2 回まで再判定して多数決。0 件ならプローブ語で 1 回だけ再検索する。

ステップ 3: 以後、写真が増えたら（自動追従）

新しい写真 30 枚が夜間に索引されると、その 30 枚だけを保存済みクエリベクトルで採点し、永続化されたスコアプール（上位 300 件の refKey→類似スコア表）へマージしてメンバーを引き直す。86,000 枚の再走査も LLM も走らない。ズレが蓄積したら（埋め込み 500 枚以上の差）、または解釈器の版が古ければ（評価規則の変更を既存アルバムへ波及させる）フル再評価で整合を取り直す。

  • 0 件でも保存する：アルバムは“生きた条件”であり、索引が進めば再評価で自然に埋まる（証拠主義）。
  • 夜間の一括処理は一枚岩（始まると譲れない）なので BackgroundYield.monolithicHeavyWorkAllowed（非アクティブ限定）を通し、アルバム間でゲート・前面復帰を確認して残りを持ち越す。フル再評価は前面復帰でアルバム間中断する。
  • refresh/finalize は in-flight ガード（isEvaluating）で常に 1 本。全メタ（86k）とカタログはループ外で 1 回だけ構築して全アルバムで共有する。
  • 再設定（検索文の変更）は解釈を破棄してやり直す。評価規則を変えたら SavedInterpretation.currentVersion を採番——版不一致はドリフト再評価の stale 判定でも拾われ、既存アルバムが夜間に自動修正される。

フェーズ 1：解釈と接地

interpretation(id:criteria:now:) は保存済みが現行版ならそれを返し、なければ FM で解釈して必ず決定的レイヤーで上書き接地する。小型 LLM の構造化出力は信用しない（ADR-23）：

  • 日付は RelativeDateParser（日英対応）が唯一の出典。LLM が出した日付範囲は捨てる。
  • 場所はライブラリの地名カタログ or 原文に実在するものだけ採用（幻覚地名の混入防止）。
  • 人物は PersonNameGrounder が命名済み顔クラスタへ接地。「太郎と花子」→ 山田太郎・山田花子（姓だけ・名だけの部分一致も解決）。
  • 視覚語・属性語は JapaneseVisualLexicon（約 170 語）が抽出し、LLM 出力とマージ。「笑っている」「綺麗な」「2人の」「だけ」は実測シグナルへのハード条件になる（S10/S12）。
  • 内容語の語彙接地は groundContentTerms：全語が語彙に完全一致なら即接地（重心不要）、そうでなければタグ重心の類似で展開。否定語は接地できなければ捨てる（不在は検証できない・ADR-100）。
  • 言い換えプローブ（最大 4）もこのとき生成して永続化（ADR-35）。以降の再評価で LLM は走らない。

フェーズ 2：検索（searchWithPool）

本体は AIAlbumSearcher.searchWithPool。純ロジックなので macOS テストで固めてある。処理順：

  1. ハード条件：QueryEvaluator.hardFilter。人物条件は peopleByRefKey（現在の顔クラスタ名）でライブ照合。属性条件は実測シグナル（笑顔・美的・人数）で評価し、証拠の無い写真は通さない（fail-closed）。
  2. 実効内容語：spec.effectiveContentTerms ＝ハード接地済みの語（人物・場所）を include から除く。内容の意図が実効的に残らないクエリ（「太郎の写真」）はハード絞り込みの結果をそのまま返す（英訳文の CLIP バンドで恣意的に欠けさせない）。
  3. 人数実測の除外：「人が写っていない」系は humanCount（86%）→ faceCount（11%）の優先で判定し、どちらの記録も無い写真は通さない（「無い＝いない」と読まない・ADR-100）。
  4. タグのハード除外：除外語がシーンタグに離散一致する写真を落とす（閾値レス・単一語 term はタグ全体一致のみ）。
  5. 肯定フレーズの選定：QueryEmbedder.phrase。除外があるとき・人物/場所接地があるときは内容語だけを使う——全文には否定語や固有名詞が含まれ、CLIP は否定を理解せず固有名詞は採点を薄めるため。
  6. 意味採点：埋め込みは loadPage（PhotoEmbedding をページング）でストリームし、全件をメモリに持たない。採点は QueryEmbedder.semanticScore（max-over-probes・除外は相対判定・絶対閾値なし）。採用は上位からの相対バンドのみ。
  7. タグ一致・字句ランキング → RRF 融合：HybridFusion.fuse([lexical, semantic, tagMatched], k: 60)。
「空を返す」判断は実障害から決めた (a) フレーズ無しでハード条件も無いときは空——旧実装は無条件で base を返し「全 68,512 枚のアルバム」が生成された。(b) 内容の意図があるのにタグ/意味/字句のどれにも当たらないときも空。(c) ただし除外だけのクエリ（「犬が写っていない」）は肯定語が無くても有効な選択なので base を返す（証拠ゲートが守る）。証拠主義（ADR-24）：索引が進めば自然に埋まる方を選ぶ。

フェーズ 3：証拠ゲートと LLM 審査

  • 証拠ゲート（evidenceGated・除外つきクエリのみ）：条件に答えられる証拠を要求する。人物除外なら人数実測か顔実測（風景タグは人の有無を語れない）。一般の除外はタグ/顔/人数のいずれか。
  • 審査（verified）：候補上位 60 件の証拠行（日付・場所・顔数・タグ）を AlbumVerifier（Foundation Models・detached utility）が keep/drop/unsure 判定。unsure は最大 2 回再判定し多数決。LLM が使えない環境では審査をスキップして融合結果をそのまま使う。

フェーズ 4：再評価（増分＋ドリフト検知）

  • 増分（refreshIncremental）：新規に埋め込みが付いた写真だけを保存済みクエリベクトルで採点し、スコアプール（上位 300 件）へマージ→メンバー再算出。採点規則はフル検索と共有（QueryEmbedder）。内容の意図が無いアルバムはハード通過分をそのまま追加。
  • ドリフト検知（refreshIfDrifted）：評価済み埋め込み数との差が 500 を超えるか、解釈器の版が古いアルバムがあればフル再評価。夜間窓（非アクティブ）でのみ実行。

コンポーザーの入力支援は同じ決定的レイヤーの再利用

AutoAlbumEngine+Suggestions（ADR-37）。サジェストチップは FaceStore / 地名カタログ / TagStore.topTags から、接地プレビューは previewInterpretation と同じ経路から作る。ヒット件数も本番と同じシグナル（属性条件含む）で数える——シグナル無しの評価は fail-closed で「綺麗な写真→0 枚」と誤表示した実障害がある。本番検索と同じ部品を使うことで「プレビューと実際の解釈がズレない」ことを構造的に保証する。スナップショットは件数変化で失効判定、プレビューは 350ms debounce、件数計算は detached。
