AI 基礎知識 — 9. 評価指標と実験設計

検索や分類の「良さ」を数値で測るための基礎。指標の定義そのものは単純だが、何を正解とみなすか（ground truth）と、どう実験を組むか（実験設計）が結果の信頼性を決める。本章も汎用の解説で、本アプリ固有の話はテストと評価の章にある。

正解集合（ground truth）が出発点

評価には「このクエリの正解はこの写真たち」という正解集合が要る。人手で毎回判断すると再現できず、感覚に引きずられる。そこでラベル付きデータセット（画像に何が写っているかの注釈が付いたコレクション）を使い、正解集合をラベルから機械的に導出する——同じ入力なら誰がいつ実行しても同じ数字になることが、指標のいちばん大事な性質。

Precision / Recall / F1

検索結果（システムが返した集合）と正解集合を突き合わせると、4 つの領域ができる：

実際に正解実際に不正解
返した真陽性 TP偽陽性 FP（混入）
返さなかった偽陰性 FN（取りこぼし）真陰性 TN
  • Precision（適合率）＝ TP / (TP + FP) — 返したもののうち正解の割合。「混ざらない」の指標。
  • Recall（再現率）＝ TP / (TP + FN) — 正解のうち返せた割合。「取りこぼさない」の指標。
  • F1 ＝ 2PR / (P + R) — 両者の調和平均。どちらかが 0 に近いと F1 も低くなる（算術平均と違い、片方だけ良くてもごまかせない）。
P と R はトレードオフ たくさん返せば Recall は上がるが Precision は下がる（逆も然り）。だから片方だけを見て改善を主張してはいけない。 どちらを優先するかはプロダクトの約束で決める——写真アルバムでは「関係ない写真が混ざる」方が 「1 枚取りこぼす」より目立つので、Precision を第一の約束にするのが普通。
Precision の落とし穴：何も返さなければ 1.0 「接地できない語は検索しない」という設計は Precision 1.0 を保つが、それは「間違えない」だけで 「解けている」わけではない。諦めを検出するには F1 か Recall を併記する （本アプリでも「クラス名比較は接地 3/10 で Precision 1.0」という数字に一度だまされかけ、 F1 で比較し直して重心方式を採用した）。逆に「正解が 0 件のクエリ」（存在しない被写体）では 0 件を返すことが正解＝このとき P=R=1 とする採点規則を明示しておく。

マクロ平均とカテゴリ別集計

クエリが 100 本あるとき、全クエリの TP/FP/FN を合算してから指標を出す（マイクロ平均）と、正解数の多い簡単なクエリが支配してしまう。クエリごとに P/R/F1 を出して単純平均する（マクロ平均）と、難しい少数派クエリの失敗が数字に現れる。さらにカテゴリ別（被写体／除外／複合…）に分けて集計すると、「どの種類のクエリが弱いか」が特定でき、改善の優先順位が数字で決まる。

Recall@K（上位 K 評価）

結果を全部見ることが前提でない UI（検索上位だけ見る）では、上位 K 件に正解が含まれる割合（Recall@K）で測る。K は UI の現実（1 画面に見える枚数など）から決める。ランキングの質を測る指標としては他に MRR・nDCG などがあるが、まず Recall@K で十分なことが多い。

アブレーション（切除実験）

「この部品は効いているのか？」に答える実験。部品を外した（または量を振った）系を作り、同じデータセット・同じ指標で比較する。効果が Δ で数値化されるので、「重いのに効いていない部品」を発見できる——機能の追加だけでなく廃止もこの方法で決められる（本アプリでは VLM キャプションの網羅率を 0%/1%/100% に振り、ΔF1=0.0001 を確認して機能ごと廃止した）。

回帰フロア（性能の下限をテストに焼く）

計測は「一度良くなった」ことしか保証しない。改善を維持するには、現状値から少し余裕を引いた下限（フロア）を自動テストにする——性能を黙って壊す変更が入ると CI が落ちる。意図的なトレードオフでフロアを割るときは、理由を記録してからフロアを更新する（数字の変更に説明責任を付ける）。

パラメータ掃引と分布ベースの判定

しきい値を 1 点だけ試して決めると、その値がデータセット固有の偶然かもしれない。候補値の格子を掃引して感度を見て、性能が安定な領域から選ぶ。また生のスコアに絶対しきい値を置くとモデルやデータが変わるたびに壊れるので、分布からの突出（z スコア＝平均から標準偏差いくつ分か）のような相対判定にすると尺度に依存しなくなる。

実験設計の落とし穴

  • 実装がテスト専用の近道を通る — 評価は必ず本番と同じコード経路で走らせる。別実装の評価は本番の劣化を検出できない。
  • 正解の分布がずれている — 索引の網羅率（全写真のうちタグ済みが 86% 等）を評価環境でも再現しないと、「未索引を『無い』と読む」型のバグを見逃す。
  • 乱数で結果が揺れる — サンプリングは決定的に（キーからのハッシュ等）。再実行で同じ数字にならない評価は議論の土台にならない。
  • 1 例で判断する — 個別の成功/失敗例は仮説の入口であって結論ではない。データセット全体の Δ で判断する。
