設計判断ハイライト（重要トップ 10）

本アプリで「効いた／学びになった」設計判断（ADR）から、特に重要な 10 個を抜粋して紹介する。各項は要点のみ。個別のバグ・性能対応の顛末（事例）は正本の case-studies.md と深掘りページへ。全件は Markdown のマスターを参照。

このページは“抜粋”、正本は Markdown 設計判断・事例の正本（マスター）はリポジトリ内の Markdown： records/decisions.md（ADR 全 37 件）と records/case-studies.md（事例 全件）。 本 HTML はそこから重要なものを取捨選択した派生物で、全件は転記しない。新しい判断・事例はまずマスターへ追記する。 詳しい顛末は 事例: メモリ / 事例: 起動 の深掘りページも参照。

設計 1. 検索の再設計＝「タグ台帳＋LLM 審査」（閾値レス） (ADR-24・ADR-23・ADR-1)

文脈: 当初は固定タグを捨て語彙ゼロの CLIP コサイン＋絶対閾値に一本化した（ADR-1）が、ライブラリ分布が不明で閾値が調整できず「除外が 97% を落とす／意味採用 0 件」が発生。小型 LLM の構造化出力も壊れた。
決定: (a) 解釈（検索文→QuerySpec・英訳）は作成時に 1 回だけ実行し永続化（ADR-23。旧・毎起動再解釈の 9.4s ハングを根治）。(b) 検索を Vision シーンタグ一致（離散・閾値レス）＋CLIP 対比＋字句の RRF 融合 → 証拠ゲート → LLM 審査（多数決）へ（ADR-24）。表示タグはシーンタグ＋ゼロショットで別途。
結果: 閾値依存がほぼ消滅し、判定根拠がタグ/キャプションで可視化。全写真へシーンタグ・CLIP 埋め込み・VLM キャプションを夜間に付与する索引が必要。

設計 2. ロジック層 / UI 層の分離（Core/UI） (ADR-3)

文脈: 副作用（PhotosKit/URLSession/SwiftData）を UI から切り離してテストしたい。
決定: *Core（SwiftUI 非依存）と *Kit（UI・@_exported import）に分割。
結果: 純ロジックを macOS で高速テスト。import は 1 つで済む。パッケージ数は増える（現在 11 個）。

設計 3. グリッドを UICollectionView に置換 (ADR-4)

文脈: 6 万件超で LazyVGrid + scrollTo のスクラバーが不安定。
決定: UIViewRepresentable で UICollectionView（diffable・プリフェッチ・contentOffset スクラバー）を採用。
結果: 大ジャンプが安定。UIKit のボイラープレートは増える。

設計 4. CLIP 埋め込みを別テーブル + Float16 (ADR-6)

文脈: 埋め込みを PhotoEnrichment に inline 格納し、全件 fetch のたび 138MB 級 blob を展開 → 写真の多い実機で起動クラッシュ。
決定: PhotoEmbedding 別テーブルへ分離し Float16 保存。メタデータ fetch は blob に触れない。
結果: 常駐が「ページ 1 枚分」に。スキーマ再構築（AutoAlbumV10）が必要。→ 事例。

設計 5. AI 検索を合成可能な QuerySpec（OR/NOT/多ファセット）へ (ADR-12)

文脈: 「ここ2年の子供」「京都か奈良の家族のお気に入り、スクショ除く」等、複雑条件・OR・NOT を柔軟に組みたい。
決定: DNF（節の OR・節内 AND・各条件 NOT）の QuerySpec。ハードは QueryEvaluator、相対日付は RelativeDateParser（日英）。
結果: 多ファセット＋OR を実現。QuerySpec は現在も解釈の内部表現として残り、採点は ADR-24 のタグ一致＋CLIP 対比＋LLM 審査へ発展した（旧フラット検索 API は撤去）。

設計 6. ModelContainer を自己修復で構築 (ADR-7)

文脈: SwiftData は破損・不整合で起動時 trap し、実機で原因不明クラッシュ。
決定: makeResilientContainer で「削除→再試行→インメモリ」とフォールバック。
結果: 起動を止めない。最悪データは失うが回復する（埋め込みは背景で再生成）。

設計 7. 重い処理は「使っていない時だけ」＋4 軸の実行条件 (ADR-25・ADR-80)

文脈: 旧ゲート「電源＋アイドル 60 秒」は、充電閲覧中に触らないと重い処理が走り出し、操作再開時にバッチ途中（最大約 27 秒）が譲れず固まった。
決定: アイドル判定を廃止し「電源＋低電力OFF＋アプリ非アクティブ＋Wi-Fi」へ。停止判定は全処理 1 枚単位。AI アルバム作成は即時プレビュー（決定的）→夜間本番化（LLM）の 2 段階。のちに実行条件を独立した 4 軸のユーザー設定（自動処理・控えめ・電源・回線＝HeavyWorkTiming・純関数で判定・ADR-80）へ発展し、AI アルバムの本番化は作成直後の即時実行（ADR-110）へ引き上げた。
結果: フォアグラウンドで重い処理がゼロになり操作が軽い。初回全量索引は「充電＋Wi-Fi＋ロック」時間帯に限定され日数を要する（エスケープハッチ＝今すぐ処理）。→ バックグラウンド。

設計 8. 共有ハード資源（ANE）は「触れる場所」で直列化する (ADR-70・ADR-73・ADR-75)

文脈: Vision の顔検出と Core ML の CLIP 推論・モデルロードが同時に Neural Engine を使うと実機でデッドロックし、Vision の perform が永久に返らない（顔スキャンが 1 枚目で固まり People=0）。単体では固まらない。以前は CLIP 埋め込みが回線ゲートで止まっており、顔スキャンが ANE を独占できていたため顕在化していなかった。
決定: ANE を使う処理を MLInferenceGate に通し同時に 1 つだけ実行する。ゲートを取るのはANE に実際に触れる場所（各ランタイム/アダプタ）の内側で、呼び出し側の夜間タガーでは包まない。待機列は前景/背景の 2 本に分け、キャンセルされた待機者は列の先頭へ繰り上げる。
結果: 学びが 2 つ。(a) 横断的な不変条件を呼び出し側に守らせる設計は必ず漏れる——実際、呼び出し側で包む方式では前景の検索経路だけが素通りし、さらにゲートの内側で 3 並列の Vision が走って不変条件を自ら破っていた。(b) 漏れは「新しい経路」ではなく「既にある別経路」で起きる。ゲート本体は PerceptionCore（顔と CLIP の共有下層）に置き、テストで優先度・キャンセル・後始末を検証している。

設計 9. モデル選定は「実測＋実機確認」で決める (ADR-31・ADR-32・ADR-34)

文脈: 画像認識が重く、CLIP / VLM の軽量化・置き換え候補を比較したい。カタログスペックでは判断できない。
決定: 共通ベンチ（Imagenette 実写＋Core ML 実行）でメモリ・速度・精度を実測して選ぶ。CLIP は INT8 量子化を採用（289→145MB・精度不変）。VLM は Florence-2-base を一度採用したが、実機 ANE/GPU の fp16 で cross-attention が破綻（全写真で無関係な文）し撤回、SmolVLM（decoder-only＝ANE 安全）へ回帰。のち SmolVLM-500M＋視覚のみ INT8 に更新し、最重量のキャプション生成はお気に入りのみに限定——最終的には網羅率アブレーションで検索寄与ゼロを計測して機能ごと廃止した（項 12・ADR-108）。
結果: 学びが 2 つ。(a) 量子化耐性は部品で非対称——連続ベクトル出力（視覚エンコーダ）は INT8 に強く、LLM デコーダは argmax が反転して壊れる。(b) Core ML の正しさは Mac だけでは検証できない——Mac の全 compute unit で正常でも実機 fp16 で壊れた。実測記録は records/model-evaluations.md。

設計 10. 検索品質は回帰ハーネスで数値検証してから直す (ADR-35)

文脈: 「自然文アルバムをもっと良く」——だが何が弱いか感覚では特定できず、直した“つもり”の劣化も検知できない。
決定: 正解ラベル付き評価セットで実パイプラインを走らせるハーネスを常設し、以後段階的に拡充した——初代（Imagenette＋28 クエリ・ADR-35）から、現在は COCO val2017（4,952 枚・123 クエリ・10 カテゴリ）＋Caltech-101（語彙接地の end-to-end）へ（ADR-104）。ベースライン計測で弱点を数値で特定し、対策（言い換えプローブ・語彙接地・実効内容語など）を同ハーネスの A/B で検証してから採用する。カテゴリ別 F1 の回帰フロアと全体 precision≥0.97 をテストで固定し、検索まわりの変更が性能を黙って壊すと落ちる。
結果: 言い換え再現率 +17〜18pt を数値で確認。以後の検索変更は同ハーネスの回帰チェックを通す。実運用で見つかった穴（人物名 0 件・除外×プローブの相互作用）も事例として正本に記録。

設計 11. 応答性の設計＝「一枚岩は非アクティブ限定・作成は即時本番化」 (ADR-107・ADR-110)

文脈: AI アルバムの操作でアプリが数十秒固まる実障害が続いた。実測で 2 つの機序を特定——(a) 途中で譲れない一枚岩の重い保守（本番化・全再評価・生成）が前面アイドルでも起動していた。(b) 高優先度の協調タスク（LLM 推論・86k 件フェッチ）が P コアを占有し、メインスレッドが実行されないのに固まる「飢餓」が起きていた。
決定: 一枚岩の保守は非アクティブ（ロック・アプリ切替）限定の厳格ゲートへ分離（トリクル系は従来どおり）。AI 推論・作成処理は utility 優先度に統一。逆にユーザーの明示操作（作成/更新）は待たせず、暫定プレビュー（1〜2 秒）→ その場で FM 解釈つき本番化（十数秒・語彙接地はキャッシュ済み重心のみ）の 2 段構成にした。
結果: 使用中の長時間フリーズを解消しつつ、レキシコン外の語（「バレエ」）も作成直後に反映される。教訓: スパン計測値はメイン復帰待ちで膨らむため、ハングの帰属はスパンでなく機序（占有か飢餓か）で判定する。

設計 12. 機能の廃止も計測で決める＝VLM キャプション削除 (ADR-108)

文脈: 最も重い AI 処理（SmolVLM・1 枚数十秒・モデル 877MB）が検索に効いているか、廃止判断の材料が要る。
決定: 網羅率アブレーション（0% / 実機 1% / 理想 100%）で全 116 クエリを計測。Δ(1%−0%) F1 = 0.0001＝寄与ゼロ、100% でも +0.008（到達には夜間窓 30 日分）と判明し、機能ごと廃止。証拠役は humanCount（86%・無償）が既に代替していた。
結果: アプリが 877MB 軽くなり、夜間窓とメモリが全量タグ・埋め込み・顔スキャンへ。廃止後の再計測で検出性能は不変（F1 0.896）を確認。互換のためデータスキーマのフィールドだけ残置。

設計 13. ハード接地語は内容語から除く（AND の構造保証） (ADR-109)

文脈: 「バレエの<人名>」にバレエと無関係の写真が混ざる実障害。解釈（spec）は正しく AND なのに、LLM が内容語にも人物名を重複させると、字句チャネル（人物名一致）が RRF 和集合経由で本人の全写真を通し、実質 OR になっていた。
決定: 評価時にハード条件（人物・場所）へ接地済みの語を内容語から除く実効内容語を導入。内容の意図が残らなければハード絞り込みの結果を返す。「X の Y」型は計測ハーネスの恒久カテゴリ（compound・7 本）として固定した。
結果: compound P=1.000（混入ゼロ）を計測で確認・回帰フロア 0.91 を常設。既存アルバムは解釈器の版上げ＋stale ドリフト再評価で夜間に自動修正。
