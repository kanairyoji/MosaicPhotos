事例: ANE デッドロック

顔スキャンが最初の 1 枚で永久に固まる——Vision の顔検出と Core ML の CLIP 推論が同時に Neural Engine (ANE) を使うと実機でだけデッドロックするという、ドキュメントのどこにも書かれていない共有ハード資源の衝突（diagnostics-19・ADR-70/73）。シミュレータでも Mac でも絶対に再現せず、しかも「以前は偶然起きない構造だった」ことが調査を難航させた。

症状

実機の夜間処理で、顔スキャンのログが faces: start — N photos の直後から一切進まない。クラッシュしない・エラーも出ない・CPU も張り付かない。Vision の VNImageRequestHandler.perform が返ってこないだけ。プロセスを再起動しても、同じ 1 枚目で再び止まる。

調査を難航させた 2 つの性質

  • 実機でしか起きない — シミュレータの Vision/Core ML は CPU 実行（ANE が存在しない）ため、同じコードが問題なく完走する。Mac の単体検証も同様。「コードは正しいのに実機で止まる」ログだけが手がかりだった。
  • 以前は偶然マスクされていた — 顔スキャン導入当初、CLIP 埋め込みは回線ゲート（Wi-Fi 必須）で止まっている時間帯が多く、顔検出が ANE を独占できていた。ゲート整理で両者が同じ夜間窓に走るようになった途端に顕在化した。「昔から動いていたコード」が新しい並走相手を得て初めて壊れる型で、直近の変更を疑う定石が通用しない。

特定

診断ログのタイムライン突き合わせで、停止時刻に必ずもう一方の ANE 利用者（CLIP 推論またはモデルロード）が走っていることを確認。仮説「ANE の同時利用で下位層がデッドロックする」を、片方を止める実験で検証——CLIP を完全停止させると顔スキャンは完走し、再開すると再び止まった。OS の下位層（Espresso/ANE スケジューラ）内部の問題であり、アプリ側から解けるのは「同時に使わない」ことだけ、と結論。

対策：MLInferenceGate（ANE の直列化）

  • ANE を使う重い処理は同時に 1 つ — 非同期セマフォ MLInferenceGate で、Vision の perform・Core ML 推論・モデルロードを直列化する。顔と CLIP の両方が使うため、共有下層パッケージ PerceptionCore に置く。
  • ゲートは「ANE に触れる場所」の内側で取る — 呼び出し側（夜間タガー）で包む設計は、新しい呼び出し経路が増えるたびに漏れる（実際、前景の検索経路が素通りしていた）。ランタイム/アダプタの内側で取れば、経路がいくつ増えても守られる。逆に外側で包むと画像ロード（ANE を使わない I/O）までゲートに入り、占有時間が無駄に伸びる。
  • 優先度つき — ユーザー操作由来の推論（検索クエリの埋め込み等）は interactive、夜間トリクルは background として、待ち行列で前者を先に通す。待ち時間は診断ログに出し（ANE gate: waited …ms）、ゲートが体感に影響していないかを実機で監視し続ける。
一般化できる教訓
  1. 共有ハード資源はコードに見えない — ANE・GPU・メモリ帯域は API 上に「排他」が現れないが、実体は共有資源。プロファイラにも「待ち」としてしか出ない。
  2. 「実機でだけ壊れる」を検証計画に織り込む — シミュレータは ANE が無い＝この種の問題を構造的に検出できない。実機の診断ログを常設する理由がここにある。
  3. 排他は資源に触れる場所の内側で — 呼び出し側の規律に頼る排他は、経路の増加とともに必ず漏れる。
  4. 「偶然動いていた」構造を疑う — 並走相手が増えた・ゲートが変わった、は「昔からのコード」を壊す立派なトリガー。

その後

このゲートは現在、顔・CLIP・Vision タグ・表示ラベラ・モデルロードのすべてを守っている。後日の性能調査（ADR-83）では「ゲートは推論だけを直列化し通信は縛らないので、クラウド写真のダウンロードは推論の裏に完全に隠せる」ことが確認され、スループット最適化の土台にもなった。
