事例: メインスレッド「飢餓」の追跡

「AI アルバムを操作するとアプリが数十秒固まる」——実測でメインスレッドが最長 20.5 秒応答しない障害を、5 本の実機ログ（diagnostics-45〜50）にわたって追跡した記録。有力仮説を検証テストで棄却し、計測値そのものの罠を突破して、真因が「占有」ではなく「飢餓」だったことを突き止めるまでの診断サーガ。教訓は一般化できる：メインが止まる機序は 2 つあり、対策がまったく違う。

症状

AI アルバムの作成・編集の直後、あらゆる操作が固まる。ウォッチドッグの記録は前面ハング 9.4 秒・10.2 秒・20.5 秒・10 秒級 ×6 連続。ユーザー表現は「いちいち固まる」「使い物にならない」。

迷走と突破（時系列）

段階やったこと分かったこと
1. 状況証拠ハング時刻とログ行の突き合わせハングが AI 評価の各スパン（aialbum.peopleMap 928ms・tagsLedger 2.3s…）と 1:1 で一致。「ModelActor の仕事がメインで走っている」仮説が最有力に
2. 仮説の検証仮説を直接試すテストを書く：ModelActor をメイン/オフメインで生成し、ジョブの実行スレッドを実測棄却。どちらの生成でもジョブはメインで走らない。有力仮説が消えた
3. 計測の罠スパン値の意味を再考スパン（await の壁時計）はメインが忙しいと「復帰待ち」で膨らむ。つまりスパンは犯人ではなく被害者だった。「suspect the previous log line」型の帰属はここで壊れる
4. 真因ログ全体を機序で読み直すメインは何も実行していない。userInitiated の協調タスク（86k 件フェッチ・FM LLM 推論）と Core ML モデルロードのコンパイルストームが P コアを占有し、メインスレッドがスケジュールされない＝「飢餓」。ウォッチドッグの ping は 10 秒間に 1 回しか届いていなかった
5. 増幅要因個々のログを精査(a) 作成ボタンに二重実行ガードが無く、フリーズ中の再タップで同一処理が 2 本並走（86k フェッチが直列化され 20.7 秒 ×2）。(b) 解釈器の版更新に伴う全アルバム再解釈がアルバムごとに 86k フェッチ＋カタログ構築を繰り返していた（約 10 秒 × 5 本）。(c) 背面で始まった一枚岩の再評価が、前面復帰後も譲れずに数分続いていた

対策（機序に対応させる）

  • 飢餓に対して：AI 推論・作成処理の優先度を utility に統一（userInitiated は UI と同格＝P コアを奪う）。スピナーで進行を見せて応答性を優先。
  • 一枚岩に対して：本番化・全再評価・自動生成（始まると譲れない処理）は非アクティブ（ロック・アプリ切替）限定の厳格ゲートへ分離（ADR-107）。トリクル系（1 枚ごとに譲れる）は従来どおり。フル再評価は前面復帰でアルバム間中断。
  • 増幅要因に対して：二重実行ガード・再評価の in-flight ガード・「全メタ＋カタログはループ外で 1 回だけ構築して共有」。
  • ユーザー体験に対して：ユーザーの明示操作（作成/更新）は逆に待たせない——即時プレビュー→その場で本番化（ADR-110）。
  • 観測に対して：MetricKit の MXHangDiagnostic を購読し、OS 採取のメインスレッド呼び出し木を診断ログへ（ADR-106）。自前ウォッチドッグで帰属できないケースの最終兵器。

結果

修正後の実機ログでは、同じ操作系列でハングは最大 1.0 秒 × 1 回まで縮小。残るのはプロセスあたり 1 回の Core ML テキスト塔ロード（約 5 秒・システム側スレッドのため優先度で抑えられない）に伴う短時間の飢餓のみで、受容とした。

一般化できる教訓
  1. 「占有」と「飢餓」を区別せよ——メインで重い処理が走っている（占有）なら移せばよいが、CPU を奪われている（飢餓）なら優先度と同時実行量の問題。対策がまったく違う。
  2. スパン計測値は「メイン復帰待ち」で膨らむ——await の壁時計をボトルネックと読んではいけない。被害者が犯人に見える。
  3. 有力仮説ほどテストで直接検証する——ModelActor 仮説は 10 分のテストで棄却でき、数時間の誤った修正を防いだ。
  4. フリーズは自己増幅する——固まると再タップされ、二重実行がさらに固める。ガードは UX 対策でもある。
